# 如何高效地进行代码评审：一位 GitHub 高级工程师的理念 - GitHub 博客

Sarah Vessels · @cheshire137

2024 年 7 月 23 日 | 16 分钟

作为 GitHub 的一名高级工程师，代码评审是我日常工作中的主要关注点之一。在过去八年里，我评审过 7000 多个拉取请求（Pull Request，PR）。为什么这么多？因为代码评审对构建优秀的软件至关重要，而另一双眼睛往往能发现你原本会错过的问题。

我认为代码评审是我工作中最重要的环节之一。事实上，每当我看到团队成员的拉取请求已经准备好接受评审时，我都会倾向于放下手头正在开发的分支（Branch），转而评审他们提出的改动。毕竟，他们的拉取请求已经通过了持续集成（Continuous Integration，CI）的重重考验，也达到了他们自己判断"完成"的标准，因此它很可能比我自己进行中的工作更接近可发布状态。我宁愿把他们的代码推到终点线，也不愿再投入不确定的时间去完成我自己的代码。

我越早提供反馈——"这里可能为 nil 并导致错误"、"这看起来是一个 n+1 查询"、"给这个方法加个方法签名会更好"——这些反馈就能越早被处理，缺陷（Bug）也能越早被修复，功能也能越早发布。

我想分享我进行代码评审的方法，希望能帮助大家发布更好的代码。

## 什么是代码评审？

严格来说，代码评审——通过 GitHub 上的拉取请求评审——允许协作者对拉取请求中提出的改动进行评论、表明他们对改动的认可，或在拉取请求被合并（Merge）之前请求进一步修改。

我把一个拉取请求视为对话的开始。我把它理解为作者在说："我认为这样能改进我们现有的东西。"代码评审是塑造产品实现方式的绝佳机会。作为代码评审者，我的工作是与作者来回讨论，通过提问、质疑假设、总体上充当"第二双眼睛"来改进他们的代码。

## 打磨你的代码评审流程

### 如何找到需要评审的拉取请求

我生活在 GitHub 通知收件箱里。它是我在浏览器中固定（pin）的少数几个标签页之一，所以随时可用。每当我等待 CI、任务间隙、开始新的一天、或者有空闲时刻时，我都喜欢查看收件箱。我要评审的大多数拉取请求都是在那里找到的。GitHub 的团队通常有一个自己当作大本营的 Slack 频道，那里是分享"已准备好评审"拉取请求的好地方——这是我发现拉取请求的另一条主要途径。

我还很幸运地使用 GitHub 的 Slack 集成，把一个 Slack 频道订阅到与我的团队相关的新拉取请求上。为了筛选哪些拉取请求会出现在 Slack 里，我会用一个团队专属的标签（label），然后在 Slack 里用这样一条 "subscribe" 命令：`/github subscribe your/repo pulls +label:"your-team-label"`。

我喜欢用这样的查询来搜索可能亟待评审的拉取请求：`is:open archived:false is:pr org:github -is:draft team-review-requested:github/relevant-codeowner-team`。用这条查询，我能找到 GitHub 组织（organization）内未归档、非草稿、且相关代码所有者（codeowner）团队被请求为评审者的拉取请求。我通常会省略 `review:required` 这个搜索限定符，因为即使某个拉取请求已有队友评审过，我仍然有兴趣评审它。毕竟，评审代码不仅帮助作者，也帮助我及时了解影响我所负责代码的改动。

### 用评审者团队管理通知

你不会希望代码改动通知到如此庞大的团队，以至于团队里每个人都觉得评审这个改动不是自己的责任。那样可能导致拉取请求要么长期无人评审而搁置，要么在应该合并之前就被合并，因为关键评审者在一堆通知里错过了它们。这两种情况都会影响产品质量。

我建议（如果有条件的话）精简你所在的代码所有者团队数量，让通知保持在可控范围。这样一来，落到你收件箱里的拉取请求就不再只是噪音，而是你真的觉得应该评审的东西。虽然大型的、包罗万象的代码所有者团队可以作为兜底方案，但它们不适合作为自动评审请求的第一线默认选择。让你的仓库（Repository）的 CODEOWNERS 文件保持组织良好，并配合定义清晰的代码边界，从而限制通知数量、帮助评审者避免通知疲劳。

另一种限制团队通知的方法是创建一个"首轮响应人"团队，然后用自动化（Automation）按排班表添加和移除团队成员。这样你的团队就能专注于日常的代码库（Codebase）工作，而按排班当值的首轮响应人则负责接收团队服务领域内拉取请求的通知。例如，你可以用 PagerDuty API 来确定某一天谁是首轮响应人，然后用 Octokit 库来添加和移除团队成员。

### 用自动化在团队间标准化代码评审

仓库级别的配置和自动化（比如使用 CODEOWNERS 文件和分支保护规则）有助于在团队间强制执行评审流程标准。其他标准，比如拉取请求里什么值得评论，则必须由我们人类来维护。请把团队内代码评审的运作方式记录下来，确保任何提供评审或提交拉取请求的人都知道如何让自己的拉取请求得到评审、预期的评审周转时间，以及使用了哪些自动化来促进评审。

有些团队用项目看板来跟踪哪些拉取请求进来了评审；我见过这种方式在一个管理共享 API 的团队里运转良好——共享 API 是一个经常被团队外部人员修改的领域。其他团队则完全依赖 GitHub 通知，我见过这在代码所有权边界划分得很紧、团队对"随到随审"很自律时运转良好。

如果你遵循的是团队特有的流程，自动化可以帮助你向团队外部的人传达预期。例如，如果很多其他团队依赖你的团队评审，你可以用机器人（bot）自动在任何请求你团队评审的拉取请求上留下评论，告诉作者什么时候能听到你们的回复。

## 什么让代码评审做得好或做得差？

好的代码评审能带来清晰度，把代码推向比起点更好的状态。

作为评审者，沟通的清晰度是关键。你要明确哪些评论是个人偏好，哪些是批准（approval）的拦路石。给你建议的方法提供一个示例，能让你的评审更上一层楼，也让你的意思更加清晰。如果你能从与拉取请求相同的仓库里给出示例，那就更好了——这通过鼓励一致的实现方式进一步支持了你的建议。

相比之下，差的代码评审缺乏清晰度。例如，没有任何评论的笼统批准或拒绝，会让拉取请求作者怀疑评审是否彻底。哪怕只是在批准的同时复述一下你对作者意图的理解，也能暴露出你和作者的理解是否一致。

对于建议何时实施含糊不清的代码评审，也会给作者带来糟糕体验。指出现有未改动的代码应该重构，或者某个额外情况应该被处理，这都没问题，但一定要说明这些是不是批准的前置条件。如果这个拉取请求不采纳你的建议也能合入，一定要说清楚。保持较小的差异（diff）、把这些改动作为单独的拉取请求另行发布，可能更稳妥。

下面这条代码评审评论展现了具体性，并清楚地传达了建议的实现方式：

"我看到你的新方法沿用了这个文件里的既有风格，接收 [X] 个参数。参数这么多会损害可读性，也暗示这个函数做了太多事。你觉得在后续的拉取请求里重构这个方法和现有的那些方法、减少它们接收的参数数量怎么样？"

这条评论做得好的地方：

- 提供了具体细节。
- 引用了具体的代码或问题。
- 为问题提出了解决方案。
- 援引了证据或给出了解释。

在光谱的另一端，这里有一些可以写得更好的评审评论示例：

"我不喜欢这个。"——评审者不喜欢什么？他/她心里有没有可以明确说出来的替代方案？

可能的改进：

- "这一行做了太多事，我们能不能简化一下以提高可读性？"
- "我觉得这会有性能问题，因为这是一个 n+1 查询。"
- "我们能不能用 [首选框架] 的解决方案，而不是自己写一套自定义实现？"

"这行不通。"——为什么这些改动行不通？

可能的改进：

- "这行不通是因为 [X]，请看这个相关 issue：[issue 链接]。"
- "这在 [拉取请求链接] 里以前试过，因为 [X] 没成功。"
- "如果你遇到 [X] 的问题，可以试试 [替代方案]。"

"我觉得这修复了一个缺陷。"——我很喜欢这个指出，但有没有更多上下文（比如一个 issue 链接）能让它更清楚？

可能的改进：

- "我觉得这修复了 [issue 链接]。"
- "这是在修复 [issue 链接] 里的那个缺陷吗？"
- "这看起来像是我们在 [失败的构建链接] 里遇到的那个缺陷。谢谢你的修复！"

## 如何给出好的代码评审

### 提问

我把拉取请求作者视为对这次改动最有上下文的人。我可以基于自己的历史经验——在 Ruby on Rails 单体应用（monolith）里、在 TypeScript 里、或在一个高流量的数据库上工作的经验——指出我看到的问题，但我信任作者对我问题的回答。我认为他们对细节的理解比我更好。

我还喜欢问那些涉及代码中假设的问题。他们处理的数据形态是什么样的？是否存在不符合该形态的数据？代码对此响应得好吗？代码是否资源密集？性能会好吗？作为评审者，我最喜欢的回应是作者提供一个自动化测试，来验证这些场景下的行为。我第二喜欢的回应是经验数据，比如来自我们数据仓库的查询结果，或者一张 Datadog 图表，说明为什么这些场景不成问题。

作为拉取请求作者，我乐于收到提问。当有人提问时，它给了我解释为什么我对自己的改动有信心、并在必要时援引 issue、查询或图表的空间。它也让我能与他人分享我的知识和经验。不仅作者能看到我的回复，其他评审者以及未来追查某个过往决策背景的读者也能看到。

### 给予肯定

除了提问，对拉取请求中你同意的部分发表评论也是好做法。这些评论能表明你读懂了正在改动的内容，或者你验证了代码中的某个假设。这里有几个例子：

- "看起来这跟这个模块里其他类使用的模式一致。"
- "谢谢你为这个加了测试！"
- "这比以前可读性好多了。"

根据我的经验，收到这样的评论也让人很受用。接受代码评审有时会让人感到疲惫。当我同时应付来自多方的提问和建议时，收到几条不要求我做任何事、反而支持和肯定我已付出努力的评论，会是一剂很好的强心针。

### 注意偏见和假设

你很容易让自己对评审者（或他们正在改动的代码区域）的偏见影响你的评审。你会习惯某人一直在一个领域工作、或拥有某种资历，于是假设他们知道自己在做什么——但每个人都会犯错。你的眼睛盯着他们的改动，你的问题核查他们的假设、验证你自己的假设，就能在部署（Deployment）之前发现问题。

我很看重写测试，因为测试能消除一部分偏见。当你写一个测试来验证代码是否正常工作，你就不必相信作者的一面之词，只需看测试是否通过——当然，前提是你把测试写对了。😅

我也很看重初级开发者向资深开发者提问，哪怕他们觉得自己的问题很傻、答案显而易见。如果对你来说并不显而易见，那这个问题就是成立的。对别人来说它也不会显而易见！提出这个问题，为作者写下答案留出空间，把这点教育保留给后来的人。

### 批准还是不批准

我把我的评审视为一道拦路的闸门，它能阻止另一个人改进我们的产品，所以我对是否批准十分慎重。我常常会有个人偏好，提出希望作者做出的可选改动，但我不会仅仅因为这些就扣着不批准。如果我对某人的拉取请求有建议，但他现在的拉取请求不会搞坏生产环境、不会对用户造成负面影响、也不会引发其他问题，我就会带着这些评论批准。作者可以选择在合并前处理我的反馈，也可以在另一个分支里跟进。

在评审代码时，要牢记你建议的重要性。为了落实你的建议而推迟发布值得吗？值得让作者经历一整个循环——看到你的反馈、做出建议的改动、等待 CI、再评审、部署、最终合并——吗？如果缺少某条建议不会让谁的处境变糟，那就让作者决定是否、以及何时做出建议的改动。

"请求修改（Request changes）"选项会阻止拉取请求被合并，直到评审者回来批准它。我很少用它，因为它通常显得过于强硬。我相信我的团队知道何时该批准一个拉取请求，所以队友的批准可以代替我的。同样，我相信拉取请求作者会尊重并考虑我的反馈，而不会因为别人批准了、我没批准就盲目合并。我几乎唯一会选"请求修改"的情况，是我认为存在立即的安全问题、并且担心他们在合并前看不到我的关切。

## 如何从代码评审中获得最大收益

### 评审你自己的代码

GitHub 高级软件工程师 Paul Smith 教会我在请别人评审之前先评审自己的拉取请求，我也建议你这样做。先过一遍，在那些不明显、或你在别人拉取请求里看到会提问的改动上留下内联评论。自我评审还能帮助判断一个拉取请求是否太大、是否应该拆分。

顺带一提：如果你在意保持拉取请求小巧，可以用 `lerebear/sizeup-action` 自动给拉取请求打上表示复杂度和大小的标签。

### 欢迎合并后的评审

如果我恰好在有人来得及评审之前就合并了拉取请求，我仍然欢迎他们评审。如果我的拉取请求搞坏了什么、或产生了意料之外的后果，在拉取请求上这样评论，会留下一条面包屑线索，帮助未来的读者追查发生了什么！

如果我在已合并的拉取请求上收到评审，我会像它合入之前一样处理反馈。也许是一条解释我观点的评论，也许是几个额外的拉取请求来迭代我最初发布的代码，也许是新建几个 issue 来记录需要额外完成的工作。

### 使用草稿拉取请求

当你新建一个拉取请求时，可以选择把它设为草稿（draft）。我大量依赖草稿阶段来表明我是否想要评审。例如，如果某个必需的 CI 构建失败了、或者我还没完成，我就会把它保持为草稿。我也倾向于对别人的拉取请求抱有同样的预期：如果是草稿，我假设作者还没准备好接受评审；如果它被标记为"已准备好评审"，我假设阻止他们部署这个拉取请求的，只剩下获得足够多的批准。

草稿状态意味着一个拉取请求尚未完成，所以在解决合并冲突、或处理评审者反馈时，我会把拉取请求移回草稿。如果我必须修改代码，我会先把拉取请求标记为草稿，以免打扰已经评审过它的人。当我把它移回"已准备好"时，会向那些评审者发送一条 GitHub 通知，让他们再看一遍。

### 保持友善

"用蜂蜜比用醋能抓到更多苍蝇"这句谚语浮上心头。我希望自己的拉取请求得到评审，所以我喜欢回复我拉取请求上的评论——尤其是当我不同意评审者时。即使我不写回复，我也常常用一个 👍 表示同意、或一个 ❤ 表示感谢。

我希望评审者相信他们的建议不会被遗忘，所以我会通过评论让他们了解进展。如果我同意他们的建议——比如进一步重构现有代码——我会这样表态，同时就"在当前拉取请求里做这个改动"表达异议。当我在后续的拉取请求里处理他们的反馈时，我会回来附上一个链接，让评审者知道他们的反馈没有被忽视。

我还会在实施了他们建议改动的后续拉取请求里提及（@）他们，并附上一句"这回应了 @某某 在 <上一个拉取请求 URL> 里的反馈"。这既为其他读者提供了背景，也是对原评审者的致谢，把这个想法的功劳归于他们。

当你兑现了在后续分支里处理反馈的承诺，就有助于与评审者建立信任，这能让他们更放心地批准你未来的拉取请求，因为他们知道你不会把东西留着不完成。

## 总结

代码评审对产品质量的重要性怎么强调都不为过，尤其是在 AI 代码生成的时代。在我的职业生涯中，很多次仅仅因为"第二双眼睛"就发现了一个缺陷、避免了一次事故（Incident）。无论是花在日常评审、打磨流程，还是构建支持它的自动化上，代码评审都完全值得投入时间。开发人员现在彻底地评审拉取请求，比之后再处理一个已经发布到生产环境的问题要更快、也更省心。

感谢你如此在意代码质量，愿意读我的代码评审理念。你最近查看过你的评审队列了吗？也许现在正是把这些想法付诸行动的好时机。
