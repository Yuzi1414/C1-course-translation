# API 不适合直接做成 MCP 工具

模型上下文协议（Model Context Protocol，MCP）如今是个大热门。它已经成为让大语言模型能够调用他人所写工具的事实标准，而这自然也把它们变成了智能体。但为一个新的 MCP 服务器编写工具并不容易，因此人们常常提议把现有 API 自动转换成 MCP 工具——通常是借助 OpenAPI 元数据（见参考文献 1、2）。

以我的经验，这条路走得通，但效果并不好。下面说说原因：

## 智能体不擅长应付大量工具

VS Code 有个众所周知的硬性上限：128 个工具——但许多模型在远未达到这个数字之前，就已经在准确调用工具上力不从心了。此外，每个工具及其描述都会占用宝贵的上下文窗口空间。

大多数 Web API 在设计时根本没考虑这些约束！当 API 是被代码调用时，为同一个产品领域堆上无数个 API 完全没问题；但如果把其中每一个 API 都映射成一个 MCP 工具，结果可能就不太妙了。

从头设计的 MCP 工具通常比单个 Web API 灵活得多，一个工具就能干好几个独立 API 的活儿。

## API 会迅速耗尽上下文窗口

设想一个 API 每次返回 100 条记录，而每条记录又非常"宽"（比如 50 个字段）。把这样的结果原样发给智能体，会消耗大量 token；即使一个查询只需少数几个字段就能满足，所有字段最终还是会全部挤进上下文窗口。

API 通常按记录条数分页，但记录之间的大小差异可能非常大。一条记录可能包含一个占 10 万 token 的大文本字段，另一条却只有 10 个。把这些 API 结果直接塞进智能体的上下文窗口是一场赌博——有时行得通，有时会直接爆炸。

数据格式也可能是个问题。如今大多数 Web API 返回 JSON，但 JSON 是一种对 token 非常不友好的格式。看这个例子：

[ { "firstName": "Alice", "lastName": "Johnson", "age": 28 }, { "firstName": "Bob", "lastName": "Smith", "age": 35 } ]

对比一下同样数据的 CSV 格式：

firstName,lastName,age
Alice,Johnson,28
Bob,Smith,35

CSV 数据简洁得多——每条记录只消耗大约一半的 token。一般来说，CSV、TSV 或 YAML（用于嵌套数据）比 JSON 是更好的选择。

这些问题没有一个是无法克服的。你可以设想自动为工具加上让智能体投射字段的参数，自动截断或总结过大的结果，自动把 JSON 结果转成 CSV（嵌套数据则用 YAML）。但我见过的大多数服务器，这些事一件都没做。

## API 没有充分发挥智能体的独特能力

API 返回结构化数据，供程序化消费。这往往是智能体从工具调用中想要的……但智能体还能处理其他更自由形式的指令。

例如，一个 ask_question 工具可以对某些文档做一次 RAG 查询，然后以纯文本形式返回信息，用来为下一次工具调用提供依据——完全跳过结构化数据。

或者，一个 search_cities 工具的调用可以返回结构化的城市列表，外加一条"接下来该调什么"的建议：

city_name,population,country,region
Tokyo,37194000,Japan,Asia
Delhi,32941000,India,Asia
Shanghai,28517000,China,Asia
Suggestion: To get more specific information (weather, attractions, demographics), try calling get_city_details with the city_name parameter.

这种分层和工具链在 MCP 服务器中可能非常高效，而如果你只是把 API 自动转换成工具，就会完全错过这些。

## 如果智能体需要调用 API，它直接调用就行

像 Claude Code 这样的智能体，如今编写并执行代码（包括调用 Web API 的脚本）的能力已经相当出色。有些人甚至据此认为，MCP 根本就没必要！

我不同意这个结论，但我认为我们应该"滑向冰球将要去的地方"。智能体的沙箱化正在快速改进，如果让智能体直接、安全地调用 API 变得容易，那我们不如直接这么做，省掉中间环节。

## 结论

智能体与 API 的典型消费者有着本质区别。从现有 API 自动创建 MCP 工具是可能的，但这样做效果多半不佳。只有当工具是围绕智能体独特的能力与局限来设计时，智能体才能发挥出最佳水平。
