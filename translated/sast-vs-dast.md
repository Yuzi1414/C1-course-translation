# SAST vs. DAST vs. RASP：应用安全测试方法对比 | Splunk

2024 年 12 月 18 日 · Shanika Wickramasinghe

全球信息安全支出预计到 2025 年将达到 2120 亿美元，较 2024 年增长 15%。据 Gartner 称，生成式 AI 的兴起和云计算的普及是这一快速增长的关键原因。这家分析机构进一步预测，到 2027 年，生成式 AI（GenAI）将参与 17% 的网络攻击。

企业需要超越传统方法的先进安全策略，以应对这些日益增长的威胁。正因如此，企业主需要了解 SAST、DAST 和 RASP 等安全解决方案，因为它们能为应用提供多层次的防护。

## 什么是 SAST？

静态应用安全测试（Static Application Security Testing，SAST）是一种白盒安全测试方法。SAST 利用应用的静态源代码或二进制文件来识别漏洞。这意味着 SAST 工具是在应用**不运行**的情况下对应用代码进行操作。

开发者使用 SAST 检测各种安全风险，例如：跨站脚本（XSS）、不安全的反序列化、缓冲区溢出，以及代码中其他 OWASP 漏洞。由于 SAST 单独无法识别运行时特有的漏洞，开发者通常需要将 SAST 与其他测试方法结合使用，以实现全面的安全保障。

SAST 是软件开发生命周期的重要组成部分，因为它能在早期检测漏洞。越早发现漏洞，修复成本就越低。由于 SAST 工具可以在开发阶段运行，开发者如今能够在产品发布到市场之前编写代码并测试上千次（！！）。

SAST 可以集成到 CI/CD 管道中，一旦集成，它就被称为「安全 DevOps」或「DevSecOps」。SAST 通过自动化实现了高度可扩展性。能够实施覆盖 SAST 技术的自动化测试，使其成为快速解决代码级风险的高效方案。

## 什么是 DAST？

动态应用安全测试（Dynamic Application Security Testing，DAST）是一种黑盒测试方法。DAST 中的「动态（Dynamic）」一词表明，这种方法是在应用**运行期间**评估其安全性。与 SAST 不同，DAST 不需要访问应用的源代码。相反，它：

模拟外部攻击者的行为。

从外部测试应用，以识别只在运行期间才出现的漏洞。

DAST 能够识别各种安全缺陷，例如拒绝服务（DoS）漏洞和不安全的服务器配置。通过模仿真实的攻击场景，DAST 工具评估应用如何响应这些模拟威胁。借助这种方法，开发者可以识别出 SAST 等静态测试方法可能遗漏的薄弱环节。

通常，开发者在软件开发生命周期的后期阶段执行 DAST，往往就在部署之前。通过在实时环境中测试应用，DAST 提供了运行时安全性的清晰概览，并支持构建能够抵御潜在攻击的、性能更好的应用。

## SAST 如何工作？

开发者使用 SAST 工具应用预定义规则和其他检测方法——例如模式匹配和数据流分析——来识别编码错误及其他漏洞。他们将这类工具集成到 IDE 或 CI/CD 管道中，以便在编码和测试阶段自动执行扫描。

### 常见的 SAST 方法

以下是 SAST 中用到的一些方法。

**模式匹配**：扫描代码库，查找已知的不安全编码实践模式。例如，使用弱加密算法或不安全的 API 调用。

**数据流分析**：追踪数据在应用中的流动方式。通过追踪不可信输入路径到敏感操作，可以识别 SQL 注入或缓冲区溢出等漏洞。

**控制流分析**：可以分析应用的控制结构。例如，通过循环和条件语句，发现逻辑缺陷或竞态条件等潜在漏洞。

**自定义规则创建**：许多工具允许开发者创建自定义规则，以落实编码最佳实践。以下是这类自定义规则的一些示例：

- 标记任何在 SQL 查询中使用未经净化输入的情况。
- 识别将用户提供的数据未经正确转义就输出到浏览器的代码。
- 高亮使用有漏洞或已废弃函数的情况，例如 JavaScript 中的 `eval()` 或 C 语言中的 `strcpy()`。
- 检测源代码中硬编码的 API 密钥和密码，并标记任何缺少对用户提供数据做输入验证的地方。

**依赖扫描**：一些 SAST 工具分析应用中使用的第三方库和框架，以识别依赖项中的漏洞。

**语义分析**：通过解读代码的含义而非仅仅其结构，SAST 工具可以检测不安全的配置或 API 的误用。

**机器学习模型**：先进的 SAST 工具整合了机器学习算法，通过分析海量数据集中的模式来识别此前未知的漏洞。

### 使用 SAST 工具时的性能考量

SAST 工具往往需要大量的 CPU 和内存资源。在分析大型代码库时，这可能是一个重大问题。对一百万行代码的完整扫描可能会消耗数 GB 的 RAM。

SAST 扫描所需的时间会因代码库规模而大幅变化，从小型项目的几分钟到企业级应用的数小时不等。这可能会影响：

- 构建管道的时间表
- 开发者的生产力

建议使用支持增量扫描的现代 SAST 工具，这样只需分析变更的代码，而无需扫描整个代码库。

此外，通过规则选择和范围定义进行性能调优至关重要。配置不当的 SAST 工具可能会不必要地分析非关键代码路径，既浪费时间又浪费资源，却无法带来安全收益。

## DAST 如何工作？

DAST 工具模拟真实世界的攻击——例如，向输入字段发送各种形式的恶意数据，观察应用如何处理它们——以识别应用行为与响应中的漏洞和薄弱环节。

### DAST 的步骤

该过程通常包含以下步骤。

**第 1 步：扫描。** 扫描 Web 应用以发现入口点（如 URL、表单和 API）。这一步会勾勒出应用的结构，并识别潜在的攻击面。

**第 2 步：攻击模拟。** 通过向应用发送精心构造的请求来模拟恶意活动。这些请求试图利用入口点，测试跨站脚本和跨站请求伪造等漏洞。

**第 3 步：漏洞检测。** 分析应用的响应以识别安全弱点。它会评估应用在受攻击时是否按预期运行。例如，可以注入恶意数据来检测 SQL 注入缺陷。

**第 4 步：报告。** 生成包含已检测漏洞和修复建议的报告。开发者可以利用报告中的结果修复已识别的问题。

现代 DAST 解决方案可以整合 AI 驱动的分析和实时数据集成等高级功能。它们自动创建测试集，动态适应应用结构，并利用机器学习算法最大限度减少误报。

### 使用 DAST 工具时的性能考量

使用 DAST 工具时，有一些性能瓶颈需要你牢记。

- DAST 工具会与运行中的应用主动交互，从而暂时增加应用服务器和 Web 服务器的 CPU 与内存占用。
- DAST 扫描期间产生的大量并发请求会消耗可观的网络带宽。
- DAST 扫描器通常通过生成唯一请求来绕过或使应用缓存失效，从而降低缓存机制的有效性。
- DAST 工具创建和管理多个测试会话，会增加应用服务器的内存占用。

为了尽可能避免此类问题或减小其影响，请遵循以下实践。

- 将 DAST 扫描安排在使用量最小的非高峰时段。
- 在与生产环境配置相同的预发布或测试（staging）环境中执行扫描。
- 使用 DAST 工具中的限流功能控制并发请求数量。
- 在扫描期间增加应用服务器的线程池。
- 为 DAST 扫描器的 IP 配置独立的缓存策略。
- 当性能阈值被超出时，实施自动暂停扫描。

## SAST vs. DAST：关键差异

下表总结了 SAST 与 DAST 之间的差异。

| 标准 | SAST | DAST |
| --- | --- | --- |
| 测试类型 | 白盒测试。可访问源代码，从内向外测试应用。 | 黑盒测试。不访问源代码，从外部测试应用。 |
| 支持的软件类型 | 支持各类软件，包括 Web 应用、Web 服务和胖客户端。 | 支持 Web 应用和 Web 服务，但通常不支持其他软件类型。 |
| 在 SDLC 中所处阶段 | 在软件开发生命周期的早期执行。 | 在 SDLC 的后期进行，通常是在部署期间或之后。 |
| 检测的漏洞 | 识别编码缺陷，如：SQL 注入、跨站脚本（XSS）、缓冲区溢出等。 | 检测运行时问题，如服务器配置错误、拒绝服务漏洞和应用级缺陷。 |
| 修复漏洞的成本 | 成本较低，因为问题在 SDLC 早期就被发现。 | 成本更高，因为漏洞发现得较晚，往往需要紧急修复才能按时部署。 |
| 运行时与环境问题 | 无法检测运行时特有或与环境相关的漏洞。 | 能够识别仅在运行期间出现或因环境因素产生的漏洞。 |
| 深度 vs. 广度 | 提供对代码级漏洞的深入洞察。 | 提供对应用外部安全风险的广泛视图。 |
| 与工具的集成 | 与 IDE 和 CI/CD 管道集成，用于自动化静态分析。 | 与 CI/CD 管道集成，用于持续的运行时测试。 |
| 误报与漏报 | 由于深入的代码分析，误报的可能性更高。 | 误报较低，但由于内部可见性有限，漏报的风险更高。 |
| 技术依赖 | 依赖编程语言和框架；需要与工具兼容。 | 独立于应用框架，因为它们从外部与应用交互。 |

## SAST 和 DAST 的优缺点

### SAST 的优点

- 在软件开发生命周期的早期识别安全漏洞。
- 分析代码库，包括基本函数和复杂分支。
- 直接作用于源代码，无需应用运行。
- 提供实时反馈和全面的洞察，例如漏洞的确切位置。
- 生成可通过仪表盘跟踪的、可导出的报告。
- 支持自动化，因此比人工代码评审更快、更高效。

### SAST 的缺点

- 经常产生大量误报，因此可能需要人工复核。
- 无法识别运行时或环境特有的漏洞，例如配置错误。
- 需要针对每种编程语言的特定工具，因此维护复杂。
- 难以理解外部库、API 和 REST 端点。

### DAST 的优点

- 识别仅在应用执行期间才出现的漏洞。
- 从外部运行，无需访问源代码。这对测试第三方应用或已编译代码很有效。
- 模拟真实攻击场景，识别 SAST 遗漏的风险。
- 独立于应用的编程语言。
- 评估整个应用和系统，包括内存消耗、资源使用和第三方接口。

### DAST 的缺点

- 只关注应用的外层，可能遗漏更深层的漏洞。
- 在 SDLC 的后期才应用，因此修复更昂贵、更耗时。
- 会遗漏 SAST 工具通过源代码分析能识别的某些漏洞。举例来说，考虑一个使用不安全随机数生成器（如 JavaScript 中的 `Math.random()`）来创建会话令牌的 Web 应用。DAST 可能会遗漏这一缺陷，因为它只测试运行时行为。（但 SAST 可以检测到它。）
- 大型项目需要自定义基础设施，并且需要应用的多个实例并行运行，因此资源密集。

## 何时使用 SAST 还是 DAST？

SAST 和 DAST 在保障 SDLC 安全方面起着互补作用。理解何时使用每一种，有助于实现全面的安全覆盖。

### 何时使用 SAST

**在早期开发阶段。** 开发者使用 SAST 在 SDLC 早期识别 SQL 注入和硬编码凭据等漏洞。通过在部署前发现这些问题，可以降低修复的成本和复杂度。

示例：SAST 工具扫描 Python 代码，标记出源代码中嵌入硬编码 API 密钥的漏洞。开发者重构代码，改用环境变量安全地存储和获取密钥。

**用于代码评审。** SAST 集成到版本控制系统中，让开发者可以在提交代码之前扫描代码。这确保只有安全的代码才会进入仓库。

示例：SAST 工具可以检测到这样一个漏洞：文件路径直接由用户输入构造而未经验证，使应用暴露于路径遍历攻击之下。开发者通过净化输入并使用安全库函数处理文件路径来修复该问题。

**在持续集成/持续部署管道中。** SAST 在 CI/CD 过程中运行自动化扫描，为开发者提供实时反馈。

### 何时使用 DAST

**预发布测试。** 开发者使用 DAST 在测试或 QA 环境中识别运行时漏洞（例如：不安全的配置、认证缺陷、访问控制不足）。

示例：DAST 工具可以检测到暴露敏感数据的数据库配置错误。然后开发者可以在部署前加固配置。

**部署后监控。** DAST 工具持续扫描已部署应用，以发现因环境变化或新出现的威胁而产生的漏洞。这保证应用随着时间的推移始终保持安全。

**测试第三方集成。** DAST 可以模仿外部攻击者的视角，识别第三方 API 或相互连接系统中的漏洞。

例如：DAST 工具测试一个 Web 应用，发现第三方支付 API 中存在漏洞——信用卡信息通过未加密的 HTTP 连接传输。开发者通过强制所有 API 通信使用 HTTPS 来解决该问题。

## 哪个更有效：SAST 还是 DAST？

SAST 或 DAST 的有效性取决于：

- SDLC 所处阶段
- 要处理的漏洞类型

SAST 在早期开发阶段效果最佳，主要用于识别源代码中的漏洞、降低成本并促进安全编码实践。相比之下，DAST 聚焦于预发布或已部署应用中的运行时漏洞，提供对配置错误和不安全集成等问题的洞察。

### 采用混合方法

与其在两者之间二选一，不如将 SAST 和 DAST 结合起来，形成一种多层次的、同时应对静态代码和运行时环境中漏洞的安全策略。SAST 可以集成到早期开发阶段，在应用编译之前检测并修复代码级问题。一旦应用在测试环境中运行，DAST 就可以识别运行时漏洞，并评估应用在受攻击条件下的行为。

在 CI/CD 管道中自动化 SAST 和 DAST 扫描，可提供持续反馈，在不牺牲安全性的前提下加快开发进程。

对于敏捷或 DevOps 环境，加入 IAST 或 RASP 等工具可以进一步增强安全。通过关联 SAST 和 DAST 的结果，组织可以实现更全面、更有效的漏洞管理。

### 使用 RASP 作为 SAST 和 DAST 的替代方案

运行时应用自我保护（Runtime Application Self-Protection，RASP）是一种先进的安全解决方案，直接安装在应用运行的服务器上。

RASP 将自身嵌入应用的运行时环境。这种集成使 RASP 能够分析应用的逻辑和数据。在分析过程中，它可以：

- 在异常行为发生时即时检测。
- 即时阻止恶意活动。

一个关键区别在于，RASP 不只是对潜在问题发出警报——它通过隔离和化解威胁来主动阻止攻击，而无需依赖外部工具。

RASP 为 SAST 和 DAST 提供了一种动态的替代方案。与分析静态代码的 SAST 和模拟外部攻击的 DAST 不同，RASP 是实时运行的。它在执行期间监控应用的行为，并通过终止会话或提醒防御者来响应实时威胁。

RASP 在保护应用免受那些绕过网络防御或在开发过程中被遗漏的漏洞侵害方面尤为有效。

然而，过度依赖 RASP 可能导致组织忽视安全编码实践。此外，由于 RASP 直接在应用的运行时环境中运行，它可能会影响应用性能。RASP 不能替代修复底层缺陷的必要性，但它能在修复进行期间提供持续保护。

正如一位 RASP 用户所评论的：

「是否使用 RASP 工具，应基于对应用具体需求和风险状况的全面评估来决定。」

## 未来是 SAST、DAST 和 RASP 相结合的 AppSec 测试

应用测试的未来在于将 SAST、DAST 和 RASP 相结合，构建全面的安全策略。随着安全挑战日益增多，将这些工具集成到 CI/CD 管道中并自动化其流程将变得至关重要。

AI 和机器学习的进步将使测试更加高效，因为它们有助于减少误报并改进威胁检测。

### 金融与金融服务业

在金融领域，AI 驱动的工具将改变漏洞的检测与缓解方式。SAST 和 DAST 将继续在开发与预发布阶段识别编码缺陷和运行时问题。

但不会止步于此：RASP 将进一步利用 AI 监控实时交易。例如，RASP 可以检测异常模式（例如：攻击者试图实时利用某个漏洞），并在通知安全团队的同时阻止这些活动。

### 物联网、边缘设备与互联设备

在物联网（IoT）领域，这些工具的组合将在保护互联设备方面发挥重要作用。具体方式如下：

- SAST 可以确认固件在开发期间不含漏洞。
- DAST 可以测试设备之间通信协议的安全性。
- 与此同时，RASP 监控已部署的设备，检测并阻止由新出现的威胁导致的未授权访问尝试或数据泄露。

同样，采用多种方法有助于物联网生态系统保持韧性。正如我们在诸多示例中所阐释的，SAST、DAST 和 RASP 的结合预示着一个应用以更强大、更主动的安全措施构建和部署的未来。

## 有韧性的安全始于主动测试

将 SAST、DAST 和 RASP 相结合，可以提供覆盖整个软件开发生命周期的稳健安全保障。

通过将这些方法集成到 CI/CD 管道中并利用 AI 的进步，组织可以主动应对新出现的威胁。这些方法共同提供了一种整体性的方法，保护现代应用免受安全漏洞的侵害。
