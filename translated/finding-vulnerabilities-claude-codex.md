我们对 AI 编码智能体查找漏洞能力的深入探索，揭示了令人惊讶的优势、关键的弱点，以及一个严重的「一致性」问题。

##### 分享

TL;DR：我们评估了 AI 编码智能体在真实代码中查找漏洞的能力有多有效。

方法：我们让 Anthropic 的 Claude Code（v1.0.32，Sonnet 4）和 OpenAI Codex（v0.2.0，o4-mini）在 11 个流行且大型的开源 Python Web 应用中查找漏洞。它们一共产出了 400 多条安全发现，由我们的安全研究团队逐一评审。

AI 编码智能体确实能发现真实漏洞：Claude Code 发现了 46 个漏洞（14% 真阳性率 TPR，86% 假阳性率 FPR），Codex 报告了 21 个漏洞（18% TPR，82% FPR）。其中约 20 个是高危漏洞。

AI 能理解上下文，却卡在数据流上：Claude Code 最擅长发现不安全的直接对象引用（IDOR）漏洞，真阳性率为 22%（13 个正确问题 / 59 个报告），但在跨多个文件和函数的污点追踪上表现吃力，SQL 注入的 TPR 仅为 5%（2/38），XSS 的 TPR 为 16%（12/74）。OpenAI Codex 几乎无法报告任何正确的 IDOR（0%（0/5）TPR），SQL 注入（0%（0/5））和 XSS（0%（0/28））表现极差，但在路径遍历（Path Traversal）上令人意外地比 Claude Code 报告了更多正确问题，TPR 达 47%（8/17）。

非确定性是一个真实的难题：在完全相同的代码库上运行完全相同的提示词多次，往往会得到截然不同的结果。在某个应用中，三次相同的运行分别产生了 3、6、然后 11 条不同的发现。

关键要点：

- 只需相对简单的、以安全为导向的提示词，AI 编码智能体就已经能在真实应用中找到真实漏洞。

- 但是：取决于漏洞类别，结果可能会相当嘈杂（假阳性率高），尤其是在 SQL 注入、XSS 和 SSRF 这类传统的注入型漏洞类别上。

- 详细的评测与基准测试是理解一种方法在查找漏洞方面有多有效的关键（这一直是对的，但在使用 LLM 这类非确定性工具时尤其如此），也是判断你的改进是否朝着正确方向前进的关键。

## 引言

在 Semgrep，我们以应用安全（AppSec）为生。我们长期在产品中将 AI 落地生产（Assistant 背后的技术、用于测试我们 AI 工作流的 promptfoo、用安全研究员分类来评测自动分类性能），并不断研究传统确定性分析与现代 AI 上下文能力的最佳组合，而不去追逐潮流。

这项研究正是这一持续使命的一部分。我们正在开启一场深入、公开的探索，以回答一个所有人都关心的问题：LLM 在源代码中查找漏洞到底有多有效？

## 关于基于 AI 的漏洞挖掘的开放研究问题

为了指导我们的研究，我们把「LLM 擅长找 bug 吗？」这个宽泛的问题拆解成更具体、可衡量的子问题。

- 基于 LLM 的漏洞查找的假阳性率和假阴性率是多少？它是否随编程语言、框架、代码库规模或漏洞类别而变化？它对代码的书写方式有多敏感？

- 假阳性和假阴性的常见原因是什么？

- 分析有多大的确定性？你每次都能得到相同的结果吗？

对于注入型漏洞，我们特别想知道：

- LLM 在追踪 source（例如用户提供的值）和 sink（例如消费原始 SQL 查询的方法）之间的用户输入方面有多有效？

- 它能否跨函数、跨文件追踪数据？

- 它能否理解净化函数和其他安全控制？

- 它能否理解来自第三方开源依赖的函数？
## 常规 SAST 基准测试的问题：缺乏真实性

在深入我们的发现之前，先聊聊我们如何衡量 AI 的表现。当前大部分研究/声明所依赖的基准测试虽然有价值，但并没有完全捕捉到真实世界代码的复杂性。

- 带有已知漏洞的应用：这些基准测试只使用带有已知漏洞的开源应用；多亏了 Kinnaird McQuade，其中许多可以在 vulnerable-apps 中找到。如果你读过这篇博客，你可能会认出其中的一些名字：WebGoat、JuiceShop、OWASP Benchmark 等。但这些基准测试有个问题：当前的 LLM 很可能已经在训练中「摄入」了这些仓库的代码，以及网上大量公开的讲解文章，这给了它们先验知识，从而扭曲了结果。它们的代码往往不够真实——充斥着大量注释、注解和变量名，这些要么暗示、要么直接描述了漏洞在代码中的位置，以及如何利用它。有时，工具的结果甚至会被提交到仓库里。（来自 javaspringvulny 的 SearchService.java）

（来自 juiceshop，挑战就藏在文件名里……）

- XBOW 为自动渗透测试工具提供了基准测试，但不适合静态分析：这些代码往往过于刻意和简单，不能代表真实应用。ZeroPath 在清洗它们时做得很不错，但只有一小部分被清洗过。此外，这些测试用例每一个都是极小的应用，专门用来触发某一个攻击场景。如果只看 Python 基准测试，XBOW 有 45 个；45 个不同的极小应用，平均不到 98 行代码、3 个 Python 文件。这对于捕捉在整个代码库或众多函数中搜索和推理的复杂性来说实在太小了。

- CVE 记忆偏差：由于 LLM 是在海量的互联网公开数据上训练的，其中就包括那些发现并修复了 CVE 的代码库本身。这就造成了一个根本性的数据污染问题。AI 可能并不是通过新颖的分析检测出漏洞，而只是认出了它在训练期间记忆的模式。

- 最近，学术界设计了诸如 CyberGym、Eyeballvul 或 SecVulEval 等基准测试。这些有了很大改进，也更接近真实世界的例子，但它们要么缺乏对现代 Web 应用的关注，要么把漏洞从更广泛的应用上下文中孤立出来。

- EyeballVul：一个更近的基准测试，来自 Timothée Chauvin，它从开源项目中抽取真实的、经人工审核的漏洞，并将它们呈现为最小的、可复现的测试用例。虽然基于真实代码，但它仍然把漏洞从更广泛的应用上下文中孤立出来，让搜索问题变得更容易。

- SecVulEval 和 CyberGym：这些套件旨在评测 C 或 C++ 中的漏洞。虽然它们在各自领域很有价值，但它们对 C 和 C++ 的关注意味着这些数据并不适用于主导现代云原生开发的 Python/JavaScript 及其他以 Web 为中心的语言。

虽然这些方法各自都有用，并且有时应该被采用，但它们未必反映现代软件开发的现实。真实世界的应用不是干净的、孤立的函数，而是依赖、框架和业务逻辑交织而成的复杂网络。

我们的方法不同。我们在 11 个大型、基于 Python、积极维护的开源项目上进行了测试，这些项目使用常见的 Web 框架（Django、Flask、FastAPI）编写。我们的方法是对此前方法的补充，我们相信它的独特之处在于：a）旨在代表真实世界中由 AI 驱动的漏洞查找（相对于小型、孤立的合成示例）；b）不受模型训练数据的污染；c）代表了大多数开发者和公司真正在构建的应用类型——使用现代语言和框架的 Web 应用。

### 我们发现的情况

Claude Code 和 Codex 在今天都很有用：它们能找到真实的安全漏洞，但非常嘈杂。整体噪音仍然很高，但它们确实在这些流行的开源 Python Web 应用中找到了真实的安全漏洞。总体而言，Claude Code 找到了 46 个漏洞（14% TPR，86% FPR），Codex 报告了 21 个漏洞（18% TPR，82% FPR）。

- 许多 IDOR 漏洞乍看是对的，Claude Code 还给出了可信的修复建议：LLM 不仅能找到这些漏洞，还能给出可信的修复，例如基于代码中已有的模式注入新的权限检查。IDOR 问题很难分类，我们不得不对其中大部分进行测试才能确定，这使真阳性率大大降低。

- Claude Code 作为好的安全护栏工具？许多发现虽然在技术上是假阳性，但仍然是很好的「护栏」建议，或者看起来像。例如，模型常常建议对一个本来已经安全的 SQL 查询做参数化。虽然这不是漏洞，但它加固了代码。我们仍然把这些视为假阳性，尽管不像其他假阳性那么严重。然而，这些代码加固建议并非总是可信。我们发现了好几个例子（尤其是在客户端 JavaScript 代码中），AI 试图修复它认为与 DOM 操作相关的问题，但实际上却破坏了代码（在我们观察到的例子中是双重转义 HTML），尽管那里本来就不存在安全问题。

- XSS 和 SQL 注入——很难把各个组件拼起来：模型难以将数据从服务端框架追踪到客户端组件（这是 XSS 的常见模式），也难以穿过复杂的应用层。它经常被静态定义的数据搞糊涂，或者无法识别服务端的净化处理。

- 重复提示词有助于获得更多结果：LLM 的概率特性意味着用略微不同的方式问同一个问题可以得到新的发现，这凸显了分析的不一致性。在同一个代码库上多次重复相同的提示词给了我们不同的答案，但最终又会绕回到相同的发现。

- OpenAI Codex 有时无法报告有效的 SARIF。在我们预期的 66 份报告中，有 9 份不是有效的 SARIF。我们考虑了这些文件里报告的所有发现，但它们不是有效的 SARIF 或 JSON。在我们尝试的所有情形中，Claude Code 都没有这个问题。
## 同样的代码、同样的 AI，每次却是不同的 bug：AI 编码智能体的非确定性问题

为了探索非确定性在实践中如何表现，我们选取了其中三个应用，用相同的提示词多次运行，每次都针对同一个安全问题：IDOR。一个模式浮现了出来：每次运行测试时，AI 的发现都不一样。

在漏洞检测的语境下，这是一个重大问题。首先，作为一名安全工程师，理想情况下我们希望得到比「希望模型这次搜得更彻底」更强的保证——保证我们的代码确实针对重要的漏洞类别被扫描过。

其次，时有时无地检测到漏洞，会给你的安全工具或漏洞管理系统带来不一致和噪音。例如，如果你在使用一个 SAST 平台、ASPM，或你自己内部构建的东西，这些系统往往假设：当一个先前检测到的漏洞不再出现时，它就已经被修复了。但对于 LLM 驱动的检测，情况未必如此，因为单次扫描可能会漏掉它，于是当后续扫描再次发现同一个问题时，就会产生一条「新」发现，导致重复的 JIRA 工单和开发者的挫败感。

以下是我们观察到的一些具体例子：

- PY-APP-007：在第一次运行中，AI 识别出一个「缺少搜索授权」的漏洞，而另外两次运行中都没有出现。第二次运行标记出了那次运行独有的问题。第三次运行则又找到了它自己的一套独特漏洞。

- PY-APP-006：类似的情况：第一次运行在用户 API 中发现了一个漏洞，而后续运行则聚焦于代码库的不同部分，例如事件摘要和笔记模块。

- PY-APP-002：这里的变异性或许最为显著。识别出的漏洞数量从第一次运行的 3 个，跳到第二次的 6 个，再到 11 个。每次运行都给出了不同的发现，彼此只有部分重叠。

那么，这背后的原因是什么？我们认为关键因素是所谓的「上下文腐烂」和「压缩」。当一个 AI 智能体被要求分析整个代码库时，它要处理海量的信息：上下文腐烂导致它无法从自己的上下文中准确检索。为了应对这一点，LLM 使用了一种有损压缩的形式（有时称为「压缩」），这意味着一些更细的推理细节，如函数名、路径等，可能会在摘要化过程中丢失。

可以把它想象成概括一部又长又复杂的小说。你会抓住主要情节，但注定会漏掉一些微妙之处和细节。同样，AI 可能会丢失某个特定的架构模式或某条微妙的数据流，导致它在某一次运行中漏掉一个漏洞，而在另一次运行中却能抓住它。我们在 PY-APP-006 中看到了一个清晰的例子：AI 提出的某个修复方案是不完整的，因为它没有复用现有的用户授权基类——这一段关键的上下文似乎在那一次运行中丢失了。

这种非确定性对我们将如何做「AI 原生 SAST」有着重大影响。一方面，AI 每次都能以不同方式「思考」的能力，意味着它可以探索更广泛的潜在攻击向量，就像一群视角多元的人类渗透测试人员。另一方面，它引入了一定程度的不确定性，可能导致混乱或误行为。

- 覆盖不完整：单次运行可能会给人一种虚假的安全感，因为它可能漏掉那些在后续运行中才会被抓住的关键漏洞。

- 缺乏可重复性：无法复现结果，使得难以验证 AI 的发现，也难以以一致、可重复的方式信任它的输出。

- 成本和时间增加：为了获得更完整的图景而需要运行多次审计，会显著增加所需的时间和计算资源。注意：对于传统软件，一旦你写好了，基本上可以「免费」地再运行一次（不包括硬件成本、电费等）。但对于重度依赖 LLM 的工具则不是这样，在这种情况下，读取一个代码库并对其推理，每次扫描可能产生几十到几百美元的 token 成本。对今天的模型而言，这个成本可能会随着时间下降，但更新的模型可能会更贵。

## Claude Code 的新 /security-review 命令有多有效？

Anthropic 为 Claude Code 发布了一个新命令，名为 /security-review。它的设计目的是在拉取请求上运行，检查变更的文件并提问，以识别特定的安全问题。你可以在这里找到它的提示词。

当在整个代码库上运行这个命令时，我们发现它所识别的安全问题相当有限。很多时候，它找不到我们在让 Claude Code 一次只搜索某一特定类型安全问题时所能得到的那些安全问题。

我们在 PY-APP-003、PY-APP-002 和 PY-APP-008 上运行了这个命令，它在所有这些应用中只找到了一个 XSS，这与我们在整体实验中得到的结果大不相同。

## 回答我们的问题

让我们基于所学，重新审视我们最初的研究问题。

- FP/FN 率是多少？对于真实世界代码上的原始 AI，假阳性率非常高，从最好的情况——Codex 的路径遍历 53%、或 Claude Code 的 IDOR 78%——到最坏的情况——Claude Code 的 SQL 注入 95%，以及 Codex 的 SQL 注入或 IDOR 100%。表现也因应用的不同而差异巨大，从 PY-APP-002（Claude Code）中 100%（10/10）的真实 IDOR，到 PY-APP-007 的 0%（0/7）。在所有应用和所有报告的问题中，Claude Code 找到了 46 个漏洞（14% TPR，86% FPR），Codex 报告了 21 个漏洞（18% TPR，82% FPR）。由于我们使用的是真实应用，我们无法在这个实验中准确衡量假阴性。我们会在即将发布的博客文章中介绍衡量假阴性率的技术！

- 它为什么会失败？我们观察到的主要弱点是，对于注入问题，模型缺乏对代码执行的深层、语义化理解。模型在过程间污点流和隐式流上力不从心——而这些恰恰是传统 SAST 引擎通常所擅长的。还有一些限制来自上下文压缩和上下文腐烂。我们将继续更详细地探索这些限制，并探索缓解它们的方案。

- 脚手架和智能体工作流有多重要？它们不只是重要，而是正在变得不可或缺。AI 在安全评审中的未来，不是单一的、单体的模型，而是一个由 AI 智能体组成的系统（包括像我们案例中的编码智能体），它们能使用工具、对证据进行推理，并协作去发现和验证漏洞。虽然我们（尚）没有数据来说明「一个能访问 Claude Code 的智能体」与「更典型的上下文工程（也就是搭建脚手架来提供所有相关代码）加推理模型」之间的差异，但我们观察到了巨大的差异：在走向报告安全问题的过程中，系统在经历复杂流程并做出有根据的决策方面的能力。话虽如此，一个反例是 Sean Heelan 通过做足够的上下文工程，让一个推理模型报告了一个漏洞（8% 的概率）。我们强烈建议你读一读他的博客文章。

- 那么这一切的成本如何？遗憾的是，我们还没能统一追踪 Claude Code 和 Codex 之间的成本。Claude Code 的总体成本是 114 美元，涵盖了所有这些漏洞和所有这些应用（不包括为验证非确定性以及 /security-review 命令所运行的）。

## 数据集：未来发布

我们今天不会发布数据集，也不会公布所分析的开源应用的名称，因为我们正处于负责任披露的过程中，正在联系应用开发者，以便修复并验证所有安全问题。一旦完成，我们就会放心地发布这些数据。

## 结论

LLM 并不是明天就能取代人类安全工程师的银弹，事实上，它们在端到端发现高危注入型漏洞方面相当薄弱。然而，它们是一个极其强大的工具。我们的研究表明，通过理解它们的优势（上下文推理）和劣势（代码的深层语义），并围绕它们利用先进的静态分析引擎构建精密的智能体系统，我们就能创造出比以往任何工具都强大得多的新一代安全工具。
