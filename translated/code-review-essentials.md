# 软件团队的代码评审要点

> 作者：Blake Smith（原文发布于 2015-02-09）

代码评审（Code Review）是任何协作型软件项目中至关重要的一环。大型软件系统通常由不止一个人编写，因此一个高效运转的软件团队需要一套稳健的流程，让团队成员和代码库本身都朝着正确的方向前进。

代码评审是一种强大的工具，它能够：

- 帮助团队成员在系统不断变化时，同步更新自己对系统的认知模型
- 确保这次改动正确地解决了问题
- 为设计的优缺点展开讨论打开空间
- 在 bug 进入生产环境之前就将其捕获
- 保持代码风格与组织方式的一致性

把这些好处想象成一个"需求层次"会很有帮助。

## 让团队成员保持同步

代码评审最关键的功能，是让团队的每个成员都朝着正确的方向前进。你无法安全地改动一个自己不理解的系统，因此代码评审能让团队在认知上保持对齐。当 Bob 为记账子系统提交一个拉取请求（pull request）时，Amy 在评审 Bob 代码的过程中，就把自己对那个系统的认知模型更新到了最新。Amy 有机会就自己不理解的部分提问，而 Bob 也从中受益——既能厘清自己的设计决策，又能把自己做的工作教给别人。一个月后，当 Amy 需要对记账子系统做改动时，她的认知模型已经是最新的、随时可以上手的。她花在阅读代码、在脑子里拼凑系统的时间更少了，而花在思考更高层的抽象与设计上的时间更多了。大家都赢，因为大家都保持同步。

## 执行一个好的拉取请求

在写任何一行改动系统的代码之前，先问自己下面这些问题：

- **"这是应该做的事吗？"** 来自客户、内部成员和其他方的需求总是相互竞争的。在深入之前，这能帮你在脑子里保持清晰的优先级。迭代/冲刺计划会议等其他流程也有助于让这件事保持在正轨上。
- **"团队是否已经同意这个改动是正确的？"** 如果没有，最好先通过邮件或当面发起一次设计讨论。当大家在改动之前就对设计达成一致时，你的改动更有可能被接受。
- **"我该如何把这个改动拆成易于评审、易于理解的小块？"** 小的改动更容易思考和理解。好的讨论源于团队能快速领会你的改动。如果你的改动体量巨大，队友们会两眼发直，你可能只会从他们那里得到几句风格上的小挑剔。
- **"我打算如何测试这个改动，以消灭 bug 并确保正确性？"** 你可能有 QA 部门，但交付高质量、可运行的软件仍是开发者的职责。易于测试的软件通常更解耦、被拆成更小的块，也更容易推理。你需要为所有改动准备一份测试计划。

我发现提前回答这些问题，从长远看帮我省去了大量头疼。你最不希望发生的事，就是花好几天编码一个改动，最后却因为它有根本性的设计缺陷或团队分歧而被拒；或者你的改动因为没人能验证其正确性而被卡住。再次强调，目标是"在改动系统的同时，让其他团队成员跟上你的改动"。问自己打算如何把工作拆成一口大小的小块、如何测试这些小块，在多个方面都有帮助：

- 它降低了风险
- 它让改动更容易推理
- 它推动你走向更好的设计

你宁可用手术刀做许多小而精确的切割，也不愿用砍刀砍出一道巨大的伤口。在大多数"加法型"场景中，我更喜欢手术刀式的开发，而把砍刀留到需要删除大块死代码的时候。

## 发送拉取请求

好，你已经赢得了团队的认可、确定改动是对的，也达成了你最初想要的设计。那么，实际发送拉取请求最高效的方式是什么？你在改动上下了苦功，自然希望其他成员关注你的拉取请求并快速反馈。该怎么做？

还记得我前面说过，代码评审最重要的部分，是让团队的集体认知模型保持对齐吗？你的其他队友很可能在做与你完全不同的东西，甚至是在系统完全不同的部分。他们的大脑处在完全不同的上下文里，所以你必须通过给他们提供评审所需的、有帮助的引导来克服这一点。这意味着写一份组织良好的描述，说明你做了哪些改动、为什么这么做，以及任何仅靠阅读代码无法获得的相关信息。别让你的队友做超出必要的心智劳动。

下面看一些拉取请求描述的好坏例子。

**糟糕的例子：**

> **标题**：修复未初始化内存的 bug
> **描述**：这是 Bob 和我之前聊过的那个 bug。我遇到编译器有点麻烦，但总算把它搞定了。大家看看有什么想法。

如果你是这份拉取请求的开发者，请停下来，设身处地站在代码评审者的角度想一想。标题含糊不清，提出的问题比回答还多：内存 bug 在哪里？这个改动有多关键？Bob 和你之前聊的那个 bug 是什么？你遇到了什么编译器麻烦？这份描述既没有提供任何关于问题的有用背景，也没有提供任何关于你改动的有用说明。如果这份拉取请求很长，评审者就不得不一头扎进代码里做"头脑体操"去拼凑上下文，之后才有机会思考这个改动如何融入系统的整体设计。

下面是一个改进后的例子，它有助于澄清这次变更集：

> **标题**：修复启动时因未初始化内存导致的进程崩溃 [#54633]
> **描述**：这个 bug 是因为我们的统计 Counter 类中的一个内存初始化错误，导致进程在启动时崩溃。我和 Bob 讨论过，我们都认为这些崩溃是一个罕见的边缘情况，不值得发布热修复版本。以下是改动摘要：
> - 把底层的 int 变量移入类初始化器，防止 Counter 中出现未初始化内存。
> - 重构 Counter 接口，简化调用方的条件逻辑，并防止进一步的 off-by-one 计数问题。
> - 新增一个能暴露该崩溃的单元测试。
> **测试**：我已确认测试套件仍然通过，并在本地手动验证了崩溃不再发生。

这份拉取请求描述有几处改进：标题足够有描述性，能给评审者一些简短上下文，并吸引他们点开邮件了解更多。评审者知道这是一次进程崩溃（这通常是很糟糕的事），而且还有一个 bug 报告编号，如果评审者有兴趣更深入地了解问题，可以阅读更多细节。新的描述还概述了问题发生的位置，帮助说明这个修复有多关键。有一份摘要列出了拉取请求中的高层结构性改动，让评审者在看代码之前就能对改动有个整体印象。代码评审者不应该对自己发现的东西感到意外。这个例子还概述了所做的测试，让评审者对改动是否经过深思熟虑、是否测试充分、是否准备好合并充满信心。让你的评审者轻松点击"合并"，就是为他们铺好成功之路。

## 评审者：给出建设性反馈

评审流程中接下来要考虑的部分，是给同行提供建设性反馈。如果目标是清晰与对齐，那么给出高质量的建设性反馈，能帮助每个人更好地理解系统，并推动代码变得更好。

避免说这样的话：

- **"这个设计是坏的。"** 为什么坏？怎样才能变得更好？这类表述会打击信心、伤害自尊。
- **"我不喜欢这个改动。"** 你为什么不喜欢？你希望它变成什么样？不喜欢某样东西是可以的，但你应该把自己的想法表达清楚，并提供关于如何改进代码的有用线索。
- **"你能把它重写得更清楚一点吗？"** 我现在这份有什么问题？我该怎么重写？哪里不清楚？这类评论本身就不清楚，也没有给出一条简单的推进路径。

相反，应该这样说：

- **"这段代码如何处理负整数？"** 这种反馈很具体，能促使开发者自己把各种结果想清楚。作为评审者，你可能知道这段代码在负整数下会崩溃，但更好的做法是让开发者自己领悟。这类问题也可能意味着存在测试缺口，或需要进一步明确范围规格。
- **"这部分让我感到困惑，我不明白为什么 A 类在和 B 类交互。"** 如果开发者没有提供有用的描述，代码结构也不够整洁，这种评论能推动设计更清晰、代码更干净。
- **"看起来你在这里打破了一个接口边界。这会对用户产生什么影响？"** 你指出了自己发现的问题，同时假定他们是有意为之、给对方留了余地。现在他们可以想清楚打破接口边界带来的、未被察觉的连锁影响，然后要么为自己的决定给出理由，要么选择改变它。

总的来说，把反馈组织成"问题"的形式，是推动清晰性、正确性的好方法，同时还能帮助开发者在未来改进设计。这也通常是高质量创意写作小组互相给反馈的方式。在创意写作场景中，说"我不喜欢这个角色"是有害的，而同一条评论可以重新组织得更清楚："在第一章里，你的角色温暖而富有同情心，现在却变得冷漠如冰。他对我来说不像一个真实的人。" 现在就有了具体的反馈，可以据此厘清问题所在。

程序员喜欢解决问题、指出问题，所以他们天生喜欢发现并指出缺陷。把代码评审当作一种"通过找出同伴代码里的问题来证明自己多聪明"的方式，这很诱人——但别这么做。代码评审是一种让更多双眼睛看改动、找出关键问题的方式，但你的目标应该是：以鼓励团队成员提升技能的方式来评审，同时解决手头的问题。

## 风格要点

花括号位置、变量/函数命名、缩进和空格问题应当处理，但它们不是优秀代码评审的核心目的（注意我把它们放在了代码评审金字塔的顶部）。如果你发现团队 90% 的时间都在纠结缩进和变量命名，那你可能正在把大家的时间浪费在本来可以基本自动化的事情上。写一份风格指南，在签入时强制执行缩进和空格问题，把时间花在更高价值的问题上。我不想贬低一致风格的重要性。恰恰相反，保持一致的、符合习惯的风格，是让你的代码库易于阅读和理解最简单的方法之一。不过，如果你把所有的代码评审都花在这些简单任务上，就要问问自己：你是否在回避更困难、更重要的工作——让团队保持认知对齐、思考更高层的设计。
