# GitHub Copilot：通过提示词注入实现远程代码执行（CVE-2025-53773）| Embrace The Red

本文介绍一次重要而令人不安的提示词注入（prompt injection）发现——它可导致开发者在 GitHub Copilot 与 VS Code 中的机器被完全攻陷。

实现方式是把 Copilot 置入 YOLO 模式，具体通过修改项目的 settings.json 文件来完成。

正如几天前在 Amp 案例中所描述的，智能体（agent）中一个容易被忽视的漏洞模式是：如果智能体能够写文件并修改自身的配置，或更新安全相关的设置，就可能导向远程代码执行（Remote Code Execution，RCE）。这种情况并不少见，也是做安全评审时应当始终排查的领域。

## 背景调研

在研究 VS Code 与 GitHub Copilot 的 Agent Mode 时，我注意到一个奇怪的行为——它可以在无需用户批准的情况下，在工作区中创建并写入文件。

这些编辑会立即持久化，而不是作为待审阅的内存态 diff；修改会立刻写入磁盘。

作为红队人员，你知道这大概不是什么好事……于是我开始研究能否利用这一点来提权并执行代码。

### YOLO 模式

接下来，我调研了 VS Code 中依赖项目/工作区文件夹内设置的特性，并很快找到了一个有趣的特性。

原来，在 .vscode/settings.json 文件中可以添加下面这一行：

```json
"chat.tools.autoApprove": true
```

这会令 GitHub Copilot 进入 YOLO 模式。

它会禁用所有用户确认，于是我们就能运行 shell 命令、浏览网页，甚至更多！

有趣的是，这虽然是一项实验性功能，但默认就存在。我并没有下载特殊版本，也没有把 VS Code 整体设为实验模式。

此外，它在 Windows、macOS 和 Linux 上都有效。

事情还不止于此！这也意味着我们可以构建真正的 AI 病毒：病毒附着在文件上，并随着开发者下载、交互被感染的文件而传播。

最后同样重要的是，为了证明我们已完全控制开发者的主机，我们展示 Copilot 可被劫持来下载恶意软件，并接入远程命令与控制（command and control，C2）服务器。

## 构建 AI 病毒

看到这里，你会注意到这基本上允许制造病毒。攻击者可以嵌入指令，一旦获得代码执行能力，就能感染其他 Git 项目（以及 RAG 数据源）以植入恶意指令，并提交更改，甚至强制推送到上游。

随着其他开发者不知不觉地传播被感染的代码，这会进一步扩散。

最后，我们还需要谈谈不可见指令！

## 建议与修复

实际上，除了我分享的 YOLO 模式示例之外，还有更多攻击角度。当微软问我是否还有其他信息时，我进一步查看，发现还有其他存在问题的地方——例如 AI 可写入的 .vscode/tasks.json，或添加伪造的恶意 MCP 服务器等——这些都能导向代码执行。而且 AI 可以重新配置项目的用户界面与配置设置。

最近我注意到开发者常使用多个智能体，因此还存在覆盖其他智能体配置文件（allow-list 的 bash 命令、添加 MCP 服务器……）的威胁，因为这些文件通常也在项目文件夹中。

理想情况下，AI 在没有得到人类事先批准前，不应能够修改文件。许多其他编辑器都会展示 diff，然后由开发者批准。

## 负责任的披露

在 2025 年 6 月 29 日报告该漏洞后，微软确认了复现并提出了几个后续问题。几周后，MSRC 指出这是他们已在跟踪的问题，将在 8 月修复。随着 8 月补丁星期二（Patch Tuesday）的发布，该问题现已修复。

向同样识别并报告了此漏洞给微软的 Persistent Security 的 Markus Vervier 致敬。你可以在他们的报告中了解更多。也向似乎同步发现了该问题的 Ari Marzuk 致敬。

感谢 MSRC 及产品团队成员的帮助，使问题得以缓解。

## 结论

这是 AI 智能体可能"越界"的又一例证！通过修改自身环境，GitHub Copilot 可以提权并执行代码，从而攻陷开发者的机器。正如我所发现的，这在智能体系统中是一个并不少见的设计缺陷。

请持续留意这类设计缺陷，它们本应在威胁建模（threat modeling）中就被轻易捕获。

干杯。
