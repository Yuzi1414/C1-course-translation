# 为智能体编写高效工具——与智能体协作

发布日期：2025 年 9 月 11 日

智能体的能力上限，取决于我们提供给它们的工具。本文将分享如何编写高质量的工具与评测，以及如何借助 Claude 让智能体为自身优化工具，从而提升性能。

模型上下文协议（Model Context Protocol，MCP）可以为大语言模型智能体赋能，提供成百上千种工具来解决现实世界任务。但我们该如何让这些工具发挥最大效能？

在本文中，我们将介绍在各种智能体式 AI 系统中提升性能的最有效技巧¹。

我们首先介绍你可以如何：

- 构建并测试工具原型；
- 借助智能体为你的工具创建并运行全面的评测；
- 与 Claude Code 等智能体协作，自动提升工具性能。

最后，我们总结出编写高质量工具的关键原则：

- 选择合适的工具来实现（以及不实现）；
- 通过命名空间为工具划分清晰的功能边界；
- 让工具向智能体返回有意义的上下文；
- 为 Token 效率优化工具响应；
- 对工具描述与规格说明做提示词工程。

构建一套评测，可以让你系统性地衡量工具的性能。你可以使用 Claude Code 基于这套评测自动优化工具。

## 什么是工具？

在计算机领域，确定性系统在给定相同输入时每次都产生相同输出，而非确定性系统——比如智能体——即使在相同初始条件下也可能产生不同的响应。

当我们以传统方式编写软件时，实际上是在确定性系统之间建立契约。例如，像 `getWeather("NYC")` 这样的函数调用，每次被调用时都会以完全相同的方式获取纽约市的天气。

工具是一种新型软件，体现的是确定性系统与非确定性智能体之间的契约。当用户问「我今天该带伞吗？」时，智能体可能会调用天气工具、根据通用知识作答，甚至先追问地点。偶尔，智能体还可能出现幻觉，或者根本不知道如何使用某个工具。

这意味着，为智能体编写软件时，我们需要从根本上重新思考方法：不能像为其他开发者或系统编写函数和应用程序编程接口（API）那样来编写工具和 MCP 服务器，而是要为智能体量身设计它们。

我们的目标是扩大智能体能够高效解决各类任务的范围，让它们借助工具追求多种多样的成功策略。幸运的是，根据我们的经验，对智能体最「顺手」的工具，对人类而言也往往出乎意料地直观易懂。

## 如何编写工具

在本节中，我们将介绍如何与智能体协作，共同编写和改进你提供给它们的工具。首先，快速搭建工具原型并在本地测试。接着，运行一套全面的评测来衡量后续改动。与智能体并肩协作，你可以反复执行「评测—改进」流程，直到你的智能体在现实任务上取得出色表现。

### 构建原型

如果不亲自上手，很难预判哪些工具对智能体是顺手的、哪些不是。首先快速搭建一个工具原型。如果你使用 Claude Code 来编写工具（有可能一次性完成），最好把工具所依赖的任何软件库、API 或 SDK（可能还包括 MCP SDK）的文档提供给 Claude。对大语言模型友好的文档通常可以在官方文档网站的扁平化 llms.txt 文件中找到（这是我们的 API 的对应文件）。

将工具封装到本地 MCP 服务器或桌面扩展（Desktop extension，DXT）中，你就能在 Claude Code 或 Claude 桌面应用里连接并测试这些工具。

要将本地 MCP 服务器连接到 Claude Code，运行 `claude mcp add <name> <command> [args...]`。

要将本地 MCP 服务器或 DXT 连接到 Claude 桌面应用，分别前往 设置（Settings）> 开发者（Developer）或 设置（Settings）> 扩展（Extensions）。

工具也可以直接传入 Anthropic API 调用，用于编程化测试。

亲自测试工具，找出粗糙之处。收集用户的反馈，围绕你期望工具所支撑的用例和提示词建立直觉。
### 运行评测

接下来，你需要通过运行评测来衡量 Claude 使用你工具的效果。首先，生成大量基于现实世界用途的评测任务。我们建议与一个智能体协作，帮助你分析结果并确定如何改进工具。你可以在我们的工具评测手册中查看这一流程的端到端演示。

生成评测任务

有了早期原型，Claude Code 可以快速探索你的工具，并创建几十组提示词与响应对。提示词应取材于现实用途，并基于真实的数据源和服务（例如内部知识库和微服务）。我们建议避免过于简单或肤浅的「沙盒」环境——它们无法以足够的复杂度对工具进行压力测试。优秀的评测任务可能需要多次工具调用，甚至多达几十次。

以下是一些优秀任务的示例：

- 下周与 Jane 安排一次会议，讨论我们最新的 Acme Corp 项目。附上上次项目规划会议的记录，并预订一间会议室。
- 客户 ID 9182 报告称，一次购买尝试被扣费了三次。找出所有相关日志条目，并判断是否有其他客户受到同一问题的影响。
- 客户 Sarah Chen 刚刚提交了取消请求。请准备一份挽留方案。确定：(1) 他们离开的原因；(2) 哪种挽留方案最有吸引力；(3) 在提出方案之前我们需要注意的任何风险因素。

而以下是一些较弱的任务：

- 下周与 jane@acme.corp 安排一次会议。
- 在支付日志中搜索 purchase_complete 和 customer_id=9182。
- 按客户 ID 45892 查找取消请求。

每个评测提示词都应配对一个可验证的响应或结果。你的验证器可以简单到在标准答案与采样响应之间做精确字符串比对，也可以进阶到让 Claude 来评判响应。要避免过于严格的验证器——它们会因格式、标点或合理的替代措辞等无关紧要的差异而拒绝正确的响应。

对于每一组提示词—响应对，你还可以（可选地）指定你期望智能体在解决任务时调用的工具，以衡量智能体在评测过程中是否成功理解了每个工具的用途。不过，由于任务可能存在多条正确的求解路径，请尽量避免过度指定或对策略过拟合。

运行评测

我们建议通过直接的大语言模型 API 调用以编程方式运行评测。使用简单的智能体循环（由交替的大语言模型 API 调用和工具调用包裹起来的 while 循环）：每个评测任务一个循环。每个评测智能体都应获得一个单独的任务提示词以及你的工具。

在评测智能体的系统提示词中，我们建议指示智能体不仅输出结构化的响应块（用于验证），还要输出推理块和反馈块。指示智能体在工具调用块和响应块之前输出这些内容，可以通过触发思维链（Chain-of-Thought，CoT）行为来提升大语言模型的有效智能。

如果你使用 Claude 运行评测，可以开启交错思考（interleaved thinking），即可「开箱即用」获得类似功能。这有助于探究智能体为何调用或不调用某些工具，并凸显工具描述与规格说明中具体需要改进之处。

除了顶层准确率，我们还建议收集其他指标，例如单次工具调用和任务的总运行时长、工具调用的总次数、Token 总消耗量以及工具错误。跟踪工具调用有助于揭示智能体采取的常见工作流，并为工具的合并提供一些机会。

分析结果

智能体是帮你发现问题并提供反馈的得力伙伴——从相互矛盾的工具描述，到低效的工具实现和令人困惑的工具模式，无所不包。然而请记住，智能体在反馈和响应中省略的内容，往往比它们写出的内容更重要。大语言模型并不总是言为心声。

观察智能体在何处卡壳或感到困惑。通读评测智能体的推理和反馈（或思维链），找出粗糙之处。检查原始记录（包括工具调用和工具响应），以捕捉智能体思维链中未明确描述的任何行为。要读懂弦外之音；记住，评测智能体未必知道正确答案和策略。

分析你的工具调用指标。大量冗余的工具调用可能意味着分页或 Token 限制参数需要调整规模；大量因无效参数导致的工具错误，可能意味着工具需要更清晰的描述或更好的示例。当我们上线 Claude 的网页搜索工具时，我们发现 Claude 会无谓地在工具的查询参数后追加「2025」，从而偏置搜索结果、降低性能（我们通过改进工具描述把 Claude 引导到正确方向上）。

### 与智能体协作

你甚至可以让智能体为你分析结果并改进工具。只需把评测智能体的记录拼接起来，粘贴到 Claude Code 中。Claude 擅长分析记录并一次性重构大量工具——例如，确保在做出新改动时，工具的实现与描述保持一致。

事实上，本文中的大部分建议都来自我们用 Claude Code 反复优化内部工具实现的实践。我们的评测构建在内部工作空间之上，映射了内部工作流的复杂度，包括真实项目、文档和消息。

我们依赖留出测试集来确保没有对「训练」评测过拟合。这些测试集揭示出，即便在「专家级」工具实现的基础上，我们仍能进一步压榨出性能提升——无论这些工具是由我们的研究员手写，还是由 Claude 自己生成。

## 编写高效工具的原则

在本节中，我们将把经验提炼为几条编写高效工具的指导原则。

### 为智能体选择合适的工具

工具越多，并不总能带来更好的结果。我们观察到的一个常见错误是：工具只是对现有软件功能或 API 端点的简单封装——而不考虑这些工具是否适合智能体。这是因为智能体相对于传统软件有着截然不同的「可供性」（affordances）——也就是说，它们对能用这些工具采取哪些潜在行动的感知方式不同。

大语言模型智能体的「上下文」是有限的（即它们一次能处理的信息量有上限），而计算机内存廉价且充裕。以在通讯录中查找联系人为例：传统软件程序可以高效地逐个存储和处理联系人列表，检查完一个再继续下一个。

然而，如果大语言模型智能体使用一个返回「所有」联系人的工具，然后不得不逐 Token 通读每一个，那就是把有限的上下文空间浪费在无关信息上（想象一下在通讯录中查找联系人，却要从头到尾一页页翻——也就是暴力搜索）。更好、更自然的做法（无论对智能体还是人类）是直接跳到相关的页面（比如按字母顺序查找）。

我们建议围绕特定的高影响力工作流构建几个经过深思熟虑的工具，使其与你的评测任务相匹配，并在此基础上逐步扩展。在通讯录这个例子里，你可以选择实现 `search_contacts` 或 `message_contact` 工具，而不是 `list_contacts` 工具。

工具可以整合功能，在底层处理可能多个彼此独立的操作（或 API 调用）。例如，工具可以用相关元数据丰富工具响应，或在一次工具调用中处理频繁串联的多步骤任务。

以下是一些示例：

- 与其实现 `list_users`、`list_events` 和 `create_event` 工具，不如考虑实现一个 `schedule_event` 工具，它会查找空闲时间并安排事件。
- 与其实现 `read_logs` 工具，不如考虑实现一个 `search_logs` 工具，它只返回相关日志行及其上下文。
- 与其实现 `get_customer_by_id`、`list_transactions` 和 `list_notes` 工具，不如实现一个 `get_customer_context` 工具，一次性汇总客户近期所有相关信息。

确保你构建的每个工具都有清晰、独特的目的。工具应该让智能体能够像人类一样（在获得相同底层资源的前提下）分解并解决任务，同时减少本会被中间输出消耗的上下文。

工具过多或工具重叠也会分散智能体的注意力，使其无法追求高效的策略。对你构建（或不构建）的工具做审慎、有选择的规划，真的会大有裨益。

### 为工具划分命名空间

你的 AI 智能体可能会接触到几十个 MCP 服务器和成百上千种不同的工具——包括其他开发者编写的工具。当工具在功能上重叠或用途含糊时，智能体可能会困惑该用哪个。

命名空间（用共同前缀把相关工具归为一组）有助于在大量工具之间划分边界；MCP 客户端有时默认就这么做。例如，按服务划分命名空间（如 `asana_search`、`jira_search`）以及按资源划分（如 `asana_projects_search`、`asana_users_search`），可以帮助智能体在恰当的时机选择恰当的工具。

我们发现，在基于前缀与基于后缀的命名空间之间做选择，对工具调用评测有着不可忽视的影响。影响因大语言模型而异，我们鼓励你根据自己的评测来选择命名方案。

智能体可能调错工具、用错参数调用正确的工具、调用太少工具，或错误地处理工具响应。通过有选择地实现那些名称能反映任务自然划分的工具，你可以同时减少加载进智能体上下文的工具和工具描述数量，并把智能体式计算从智能体的上下文中卸载回工具调用本身。这能降低智能体整体犯错的风险。

### 让工具返回有意义的上下文

同理，工具实现应只向智能体返回高信息密度的内容。它们应优先考虑上下文相关性而非灵活性，并摒弃底层的技术标识符（例如 `uuid`、`256px_image_url`、`mime_type`）。像 `name`、`image_url` 和 `file_type` 这样的字段，更有可能直接指导智能体的下游动作和响应。

与晦涩难懂的标识符相比，智能体处理自然语言名称、术语或标识符的成功率也明显更高。我们发现，仅仅把任意的字母数字 UUID 解析为语义上更有意义、更易理解的语言（甚至是从 0 开始的 ID 方案），就能通过减少幻觉显著提升 Claude 在检索任务中的精确度。

在某些情况下，智能体可能需要同时与自然语言和技术标识符两种输出打交道，哪怕只是为了触发下游工具调用（例如 `search_user(name='jane')` → `send_message(id=12345)`）。你可以通过在工具中暴露一个简单的 `response_format` 枚举参数来同时满足两者，让智能体控制工具返回「简洁」（concise）还是「详细」（detailed）响应（见下图）。

你可以增加更多格式以获得更大灵活性，类似于 GraphQL——你可以精确选择想接收哪些信息。下面是一个用于控制工具响应详略程度的 ResponseFormat 枚举示例：

```
enum ResponseFormat { DETAILED = "detailed", CONCISE = "concise" }
```

### 为 Token 效率优化工具响应

优化上下文的质量固然重要，但优化工具响应返回给智能体的上下文数量也同样重要。

对于任何可能消耗大量上下文的工具响应，我们建议综合运用分页、范围选择、过滤和/或截断，并设置合理的默认参数值。对于 Claude Code，我们默认把工具响应限制在 25,000 个 Token 以内。我们预期智能体的有效上下文长度会随时间增长，但对上下文高效工具的需求将持续存在。

如果你选择截断响应，务必用有用的指令来引导智能体。你可以直接鼓励智能体采取更省 Token 的策略，例如在知识检索任务中做多次小范围、有针对性的搜索，而不是一次宽泛的搜索。类似地，如果某次工具调用报错（例如输入校验阶段），你可以对错误响应做提示词工程，清晰传达具体且可操作的改进，而不是晦涩的错误码或堆栈回溯。

### 对工具描述做提示词工程

现在我们来到改进工具最有效的方法之一：对工具描述和规格说明做提示词工程。由于这些内容会加载进智能体的上下文，它们可以共同引导智能体走向高效的工具调用行为。

在编写工具描述和规格说明时，想一想你会如何向团队里新来的同事介绍这个工具。想想你可能会隐含带入的上下文——专门的查询格式、冷僻术语的定义、底层资源之间的关系——并把它们显式地写出来。通过清晰描述（并用严格的数据模型强制约束）预期的输入和输出来避免歧义。尤其是输入参数应命名明确：与其用名为 `user` 的参数，不如用名为 `user_id` 的参数。

借助你的评测，你可以更有把握地衡量提示词工程的效果。即便对工具描述做微小改进，也可能带来显著提升。在我们对工具描述做了精确改进之后，Claude Sonnet 3.5 在 SWE-bench Verified 评测上取得了最先进的表现，错误率大幅下降、任务完成度提升。

你可以在我们的《开发者指南》中找到更多工具定义的最佳实践。如果你在为 Claude 构建工具，我们还建议阅读工具是如何动态加载进 Claude 系统提示词的。最后，如果你在为 MCP 服务器编写工具，工具注解（tool annotations）有助于披露哪些工具需要开放世界访问，或哪些工具会做出破坏性更改。

## 展望

要为智能体构建高效的工具，我们需要把软件开发实践从可预测的确定性模式，重新转向非确定性模式。

通过本文所述的迭代式、评测驱动流程，我们识别出让工具成功的一致模式：高效的工具定义明确、目标清晰，审慎地使用智能体上下文，能够在多样工作流中组合使用，并让智能体能够直观地解决现实任务。

展望未来，我们预期智能体与世界交互的具体机制将会演进——从 MCP 协议的更新，到底层大语言模型本身的升级。凭借系统化、评测驱动的智能体工具改进方法，我们可以确保：随着智能体越来越强大，它们所使用的工具也会随之演进。
