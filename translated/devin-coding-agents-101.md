# 编码智能体 101：真正把事情做成的艺术

现在是 2025 年。编码智能体（Coding Agent）并不是魔法，但它们已经是我们最接近魔法的东西。我们注意到，一些工程师——尤其是高级到资深级别的工程师——比别人更快地取得成功。在这里，我们分享一些来自我们客户和我们自己经验的顶级经验教训。

关于本指南：

## 与产品无关

我们讨论的技巧将帮助你在使用任何编码智能体时取得成功。

## 战术性

我们提供我们最喜欢的可操作建议。

## 技术性

虽然编码智能体对许多人都有价值，但本指南是面向工程师编写的。

开发工具一直在快速演进。十年前，是自动补全和智能感知，能够建议方法名并执行程序化的重构。四年前，是副驾驶（Copilot）和 Tab 补全，能够为你写出接下来的几行代码。两年前，是生成式聊天机器人，能够辅助你的开发并为你生成整个文件。如今，是自主智能体，能够在极少人工干预的情况下，从初始描述一路做到最终的拉取请求（Pull Request，PR）。过去两年里，我们通过构建 Devin 专注于实现这一愿景。如今，人们对自主智能体的兴趣达到了新的高度，尤其是随着类似产品的近期发布 [1] 除 Devin 外，近期的一些发布包括 OpenAI 的 Codex 和 Google 的 Jules。一些本地智能体，如 Cursor 和 Claude Code，可以在并行工作区中运行，以复制类似的效果。这些智能体可以以多种形式出现，包括 Web 应用、移动应用，以及与 Slack、GitHub、Linear 和 Jira 等流行工具的集成。

虽然人类与 AI 助手搭配能比任何 AI 单独完成更多工作，但自主智能体端到端处理任务的能力带来了全新水平的多任务处理，把每位工程师都变成了工程经理。

适应与这些新 AI 同事高效协作可能需要一些时间。有趣的是，我们观察到，高级到资深级别的工程师往往能最快地采用并熟练掌握这些工具。最终，这些工具将在所有工程级别中普及。基于我们的经验和客户反馈，我们想分享关键见解和经验教训，帮助每个人成功地将这些工具整合到他们的工作流程中。

## 提示词基础

这些基本准则将帮助你在 2025 年有效地与编码智能体交互。如果你什么都记不住，至少也要记住这些。

### 说明你想要事情如何完成，而不仅仅是要什么

把智能体想象成一个初级编码伙伴，其决策可能不可靠。简单的任务可以直接描述，但对于更复杂的任务，从一开始就清楚地概述你偏好的方法。提前向智能体提供整体架构和逻辑，不仅能提高它成功的机会，还能减少你审查代码的时间，因为你已经熟悉了预期的方法。

#### 示例：

与其说"添加单元测试（Unit Test）"，不如指定要测试的功能、识别重要的边界情况，并澄清需要模拟（mock）什么（如果有的话）。

### 告诉智能体从哪里开始

想一想如果是你自己处理这个任务，你会从哪里开始。即使你不知道具体的文件或函数名，也要提到相关的仓库、文档和涉及的关键组件。清楚地指出这些要素可以最大限度地减少浪费的精力和困惑。

#### 示例：

"请为我们的代码添加对 Google 模型的支持。你应该查看最新文档 [此处](link)，并在模型组目录中创建一个新的实现文件"

### 练习防御性提示词

想象一下把同样的提示词（Prompt）交给一个新来的实习生。哪里可能产生困惑或错误？预判这些点，并主动澄清你的指令以避免歧义。

#### 示例：

"请修复我们搜索模块的 C++ 绑定，以通过新的单元测试。注意，你可能需要在每次修改代码后重新编译绑定，然后再测试。"

### 让智能体访问 CI、测试、类型和代码检查工具

智能体的很多魔法来自于它修复自己的错误并根据错误信息迭代的能力。通过类型检查器、代码检查工具（Linter）和单元测试等工具提供强大的反馈循环，可以极大地提升它们的性能。考虑使用带类型的 Python 而不是普通 Python，或者使用 TypeScript 而不是 JavaScript。教你的智能体如何运行常见的检查和测试，确保它拥有所有必要的包和访问权限。如果智能体能与浏览器交互，请提供运行你的前端开发环境的清晰说明。

#### 示例：

我们的团队从大部分无类型的 Python SDK 过渡到完全有类型的 SDK（这也是一个非常适合编码智能体处理的任务）。

### 发挥你的专业能力

当你熟悉自己的代码库（Codebase）时，以上所有事情都会变得更容易。即使是简单的任务，也能受益于你验证逻辑和结果的能力。人工监督仍然至关重要——最终，你对代码的最终正确性负责。所有权和验证将继续是人类工程师的关键职责，即使这些工具变得越来越复杂。

## 在工作流程中使用智能体

一旦你掌握了与智能体对话的基础，就该把这些 AI 助手带入你的日常工作流程了。以下是一些让智能体成为你日常工作一部分的实用方法：

### 立即接新任务

想象一下，一位队友给你发消息："嘿，我们能快速构建 X 吗？"或者"我们需要调整一下 Y。"不要让它打断你的心流，只需给一个自主智能体发送一条快速提示词来调查或做出修改。这让你能够专注于主要任务。有一个有趣的副项目想法？需要快速制作原型、抓取数据或复现研究？把它委托给智能体，稍后再回来查看。

#### 示例：

许多团队在讨论 Bug 修复或小的功能更新时，只需在 Slack 上 @Devin 即可。

### 随时随地写代码

想象一下，你在通勤或旅行时突然出现一个紧急 Bug，或者你意识到自己可能在代码里留下了一个错误。别担心！自主智能体通常支持移动访问，让你能立即处理这些问题。无论是通过 Slack 的移动应用还是专门的移动应用，许多智能体都让你能在路上解决问题，即使你的 Wi-Fi 不稳定。

#### 示例：

拥有这种灵活性让我们自己的团队在乘车和飞行途中都变得更加高效。

### 把杂活交给它

在为了旧的提交而做二分查找、或者为新功能更新文档时卡住了？把这些重复性任务交给你的智能体。你将节省宝贵的时间，并专注于更有创造性和更有影响力的工作。

#### 示例：

在我们的团队中，工程师发布一个改动后，再由智能体更新所有相关文档和面向用户的文案，是很常见的做法。

### 跳过分析瘫痪

卡在决定一次重构是否真的能简化你的代码？在两个架构方案之间无法抉择？让你的智能体把两个方案都实现出来。有了具体的例子可以比较，决策就变得简单明了，而且丢弃某个方案也不会伤害任何人的感情。

#### 示例：

在为文本框在 Lexical 和 Slate 之间做选择时，我们让智能体各自实现了一个。Slate 因为提供了更好的最终结果而胜出。

设置你的 CI/CD 流水线，让它随着每个新拉取请求自动创建预览部署，给你一个即时的在线 URL。这在审查由 AI 智能体完成的前端任务时特别方便。

## 委托更大的工单

随着你的拉取请求的规模和复杂度增长到不止几个文件，一次性处理它们就变得有挑战性了。然而，掌握如何委托中型到大型任务（通常是 1-6 小时的工作量），正是自主智能体能带来最高投资回报的地方。与其只节省几分钟，你可以赢回数小时的生产力。较小的任务可能毫不费力地完成，但拉伸智能体的能力去处理更大的任务，会带来最大的回报。

### 自动化你的初稿

对于大型任务，使用自主智能体为你的拉取请求创建一个初始草稿，可以启动进展并大幅削减你的工作量。这里的成功取决于你是否提前清楚地传达你期望的方法。把自己想象成指导初级开发者的架构师。清晰、详细的指令有助于避免把时间浪费在纠正智能体代码中的根本性误解上。

| 领域 | 起草 | 精修 |
| --- | --- | --- |
| 新闻业 | 记者收集初始信息，撰写文章初稿。 | 编辑审查草稿、核查事实、润色，并最终定稿发布。 |
| 餐厅 | 后厨帮工准备食材，制作初步菜品。 | 副厨添加调味料，调整菜品使其味道更好，然后再端给食客。 |
| 编程 | 自主智能体根据初始计划着手处理任务，并创建第一版解决方案草稿。 | 人类开发者审查草稿拉取请求，给出反馈，并在合并前添加人工精修。 |

🛑 请记住，大型任务（目前）还不完全是无人工参与的。对于更有挑战性的任务，要预期多轮反馈循环，并为润色预期一些人工精修。一个现实的目标是节省约 80% 的时间，而不是完全自动化，你的专业能力对于验证和最终质量保证仍然至关重要。

### 共同编写 PRD

对于复杂或定义模糊的任务，与你的自主智能体协作制定详细计划会非常有效。如果你一开始不了解每一个细节或需求，那完全没问题。首先提示你的智能体去探索发现性问题，比如"我们的认证系统是如何工作的？"或者"哪些服务可能受到影响？"你也可以让智能体提前识别出需要你确认的具体相关代码目标。

某些智能体，如 Devin 和 Claude Code，提供专门的规划模式，专注于阅读和探索现有代码，而不是立即修改它。如果你希望在委托任务前做更深入的准备，专门的代码库搜索工具（如 deepwiki.com 和 Devin Search）可以快速提供对你的代码库的洞察，帮助简化流程。

### 设置检查点

对于多部分任务，尤其是涉及多个代码库的任务，在过程中建立清晰的检查点：

计划 → 实现一个块 → 测试 → 修复 → 检查点评审 → 下一个块

明确要求在每一个重要阶段之后暂停，特别是对于跨越多个层（例如数据库、后端、前端）构建的复杂功能。使用这些检查点来确保实现符合你的预期，澄清疑问（例如"解释一下认证流程并确认其安全性"），并尽早纠正方向，以避免级联问题。

#### 示例：

"我想让你实现这个功能，它将横跨我们的数据库、后端和多个前端界面。请先规划出所需的数据库 schema 变更，完成后告诉我，以便我应用迁移。" -> "现在请实现后端变更并添加测试，以确保 XYZ 正常工作。完成后告诉我" -> "现在在我们的 Web 和移动界面中都实现这些变更，以调用新的后端接口"

### 教它验证自己的工作

在给出反馈时，不要只是指出问题（"这个函数不能用"）。清楚地阐述你的测试流程，使智能体能够独立验证未来的任务。对于你会频繁重复的测试模式，将它们整合进你智能体的永久知识库（参见"添加到智能体的知识库"）。

#### 示例：

在 Devin 中，我们积极地提示用户将关键的测试流程保存到智能体的持续记忆中，以简化未来的交互。

### 在 AI 热点区域提高测试覆盖率

目前，智能体还无法完全做到交互式地彻底测试所有场景。在 AI 大量修改的区域提高测试覆盖率，可以确保你对智能体的输出有更大的信心。可靠的测试意味着看起来正确的代码可以放心地合并，无需担忧。

#### 示例：

我们的团队在把某个关键代码段的实现从 Python 翻译成 C 之前，先强化了该部分的单元测试。

## 自动化工作流程

智能体响应传入事件的速度比人类快得多，而且它们比人类同事更愿意做枯燥、重复的工作。

### 为你最重复的工作创建快捷方式

工程团队经常会遇到重复性、例行的任务。这些任务非常适合用智能体来自动化。常见的例子包括：

- 功能开关移除
- 依赖升级
- 为新功能的拉取请求修复和添加测试

要高效地建立这些，经验丰富的工程师通常会创建一个健壮、可复用的提示词模板 [2] 在 Devin 中，这些被称为 playbook（剧本），可以针对这些场景反复运行。

#### 示例：

我们的一位客户每当开发新功能时，会自动触发三个专门编写单元测试的智能体。

### 智能代码评审与强制执行

虽然已经有专门的快速代码评审工具 [3] 例如 Greptile 和 CodeRabbit，自主智能体可以是一个有趣的选择，能提供更准确的洞察，特别是如果它们已经索引了你仓库的功能。

#### 示例：

在 Cognition，我们喜欢维护一份工程师最常犯错误的清单，并把这份清单提交到代码库中。然后，我们不是编写传统的 lint 规则来捕获这些错误（这通常是不可能的），而是让一个智能体在每个新拉取请求上运行，以检查这些错误。

### 接入故障与告警

你还可以设置自主智能体，让它们在响应特定事件时自动触发。例如，Devin 提供了一个易于访问的 API，其他智能体可以通过 CLI 命令集成到自定义工作流程中。这些设置与 MCP 配合使用时效果尤佳，可以接入第三方错误日志。

⚠️ 当涉及到对生产服务中的问题进行分诊时，AI 的调试技能并不那么出色。与其让 AI 在问题出现时端到端地修复 Bug，更实际的做法通常是让 AI 只标记最可疑的错误、变更等。

### 环境设置

没有什么比不完整或不匹配的环境更能拖慢智能体的速度了。为了保持平稳运行，让你的智能体设置与团队完全一致。这包括语言版本、包依赖和自动化检查。例如，pre-commit 应该安装在智能体的环境中，环境配置（密钥、语言版本、虚拟环境、浏览器登录）应该使用 .envrc 或自定义配置的 .bashrc 等工具自动加载。

## 自主智能体的局限

### 调试技能有限

Bug 报告可能看起来出奇地简单。但许多 Bug 往往不仅需要访问数据库和日志，还需要超出当今大多数 AI 智能体水平的调试能力。如果使用 AI 来辅助调试，我们建议让它列出一份可能的根因清单，而不是试图自己去调试和修复一切。然后，人类可以根据自己的经验判断哪一个才是真正的根因。但一旦知道了原因，智能体在实现修复方面仍然相当有帮助。

### 细粒度视觉推理能力差

一般来说，当今的模型在匹配设计截图或 Figma 模型所需的细节水平上，并不具备出色的视觉推理能力。它们在可以用代码级别描述的视觉内容上最为可靠（例如给它来自 Figma 的代码）。如果你希望它匹配你的视觉风格，应该使用一个带可复用组件的良好设计系统。

### 知识截止

每当你想使用一个新库时，都应该明确地把它指向最新的文档。否则，由于预训练基础模型的知识截止，大多数智能体会假设这些库的旧模式。如果你把它指向文档，一个优秀的智能体可以克服这一点，但你必须留意这一点（记住，智能体甚至不知道这些库有新版本）。

实践考量

## 管理时间与减少损失

并非每次使用智能体都会成功。在 2025 年，这些智能体的结果确实存在一些真实的方差。这份工作的一部分，就是学会以这样一种方式使用智能体，以最大化获得成功结果的机会，同时最小化浪费的时间和 Token。

### 愿意更早地止损

对于刚开始使用智能体的人来说，一个常见的错误是，即使智能体的工作已经偏离轨道，他们也执着于让一次交互成功。如果你发现自己想"它在无视我的指令"或"这件事在原地打转"，你应该可以接受终止那次对话或手动接管。发送更多消息，更可能表明你的任务本身复杂度超过了智能体的能力，而不是某个可以纠正的简单错误。

### 分散你的实验

如果你是刚开始与智能体协作，我们建议你在开始时分散下注。尝试一系列不同的提示词和想法。在那些你看到智能体天生表现良好的任务类型上加大投入——在它们表现不好的任务上及时止损。不要觉得每次都必须强迫你的智能体取得成功。

### 没有进展时就重新开始

与人类相比，在智能体身上，重新开始是正确答案的频率要高得多。如果你给智能体分配了一个任务，而它在回应反馈或纠正方向上苦苦挣扎，那么用一个新智能体从头开始，并一次性给出所有指令，往往能更快地取得成功。智能体修复一个被搞乱的环境的能力，远不如它从零开始吐出崭新代码的能力。

实践考量

## 安全与权限

### 为你的智能体创建账户

一个一次性的邮箱有助于安全地测试网站。如果你的智能体需要访问云资源，为它创建自定义的 IAM 角色。

### 给它一个开发 / 预发布环境

理想情况下，智能体使用与你团队工程师相同的测试设置。我们建议完全避免让它访问生产服务。在使用远程智能体时，你可以在智能体的远程机器上运行完全隔离的测试环境。

### 只读 API 密钥

在可能的情况下，给它只读访问权限。我们发现，任何与外部服务交互的脚本，由人类手动运行仍然是很有帮助的。

## 前方的大变革

我们坚信软件工程师不会消失。即使编码智能体变得越来越聪明、越来越有能力，深厚的技术专长和对代码库的深入了解仍然是无价之宝。对你项目、系统和代码的真正所有权，如今比以往任何时候都更加关键。在我们今天的团队中，工程师被期望监督多个系统，同时仍保持深入的理解和审慎的判断。随着自动化放大你的影响力，同时处理并行任务的能力不仅会变得可能；它将成为必需。我们很高兴分享我们在为组织准备这一转变过程中收集到的见解，让你和你的团队也能在不断演进的软件开发世界中茁壮成长。
