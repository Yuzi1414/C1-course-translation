# 长上下文为何失效

> 管理好你的上下文，是让智能体成功的关键

随着前沿模型的上下文窗口不断增长（许多模型已支持高达 100 万 token），我看到许多兴奋的讨论，认为超长上下文窗口将解锁我们梦寐以求的智能体。毕竟，只要窗口足够大，你只需把可能用到的一切——工具、文档、指令等等——统统塞进提示词里，剩下的交给模型即可。

长上下文曾一度给 RAG（检索增强生成）的热情泼了冷水（既然能全部塞进提示词，何必费心去找"最佳文档"！），又助推了 MCP（模型上下文协议）的热潮（连上每一个工具，模型就能胜任任何工作！），还点燃了人们对智能体的期待。

但现实中，更长的上下文并不会生成更好的回答。让上下文过载，可能让你的智能体和应用以出人意料的方式失效。上下文可能被毒化、变得分散注意力、令人困惑，甚至自相矛盾。这对智能体尤其致命，因为智能体恰恰依赖上下文来收集信息、综合结论、协调行动。

下面我们先梳理上下文会以哪些方式失控，再回顾一些缓解乃至完全避免上下文失效的方法。

## 上下文的几种失效模式

- **上下文毒化（Context Poisoning）**：当幻觉进入上下文
- **上下文分心（Context Distraction）**：当上下文压过了模型在训练中学到的知识
- **上下文混淆（Context Confusion）**：当多余的上下文影响了回答
- **上下文冲突（Context Clash）**：当上下文的各个部分彼此矛盾

### 上下文毒化

上下文毒化是指幻觉或其他错误进入了上下文，并被反复引用。

DeepMind 团队在 Gemini 2.5 的技术报告（我们上周解读过）中点名了上下文毒化问题。在玩《宝可梦》时，Gemini 智能体会在游玩过程中偶尔产生幻觉，从而毒化自己的上下文：

> 这种问题的一种尤其恶劣的形式是"上下文毒化"——上下文的许多部分（目标、摘要）被关于游戏状态的错误信息"毒化"，而纠正这些错误往往需要很长的时间。结果，模型可能执着于追求不可能实现或毫不相干的目标。

如果其上下文中的"目标"部分被毒化，智能体就会为追求一个根本无法达成的目标，制定荒谬的策略并反复执行同样的行为。

### 上下文分心

上下文分心是指上下文变得过长，导致模型过度关注上下文，而忽略了它在训练中学到的知识。

在智能体工作流中，随着模型不断收集信息、积累历史，上下文持续增长——这些累积的上下文可能从帮助变成了干扰。玩《宝可梦》的 Gemini 智能体清楚地展示了这一问题：

> 尽管 Gemini 2.5 Pro 支持 100 万以上 token 的上下文，但让智能体有效利用这一能力仍是一个全新的研究前沿。在这个智能体设定中，观察到当上下文显著超过 10 万 token 时，智能体倾向于重复其庞大历史中的既有动作，而不是综合出新的计划。这一现象虽然只是轶事性的，却凸显了"用于检索的长上下文"与"用于多步生成式推理的长上下文"之间的重要区别。

智能体不再利用训练所学来制定新策略，而是执着于重复其冗长上下文历史中的过往动作。

对于更小的模型，分心上限还要低得多。Databricks 的一项研究发现，Llama 3.1 405B 的正确率在大约 32k token 处就开始下降，而更小的模型下降得更早。

如果模型远在其上下文窗口被填满之前就开始掉链子，那超长上下文窗口的意义何在？一句话概括：**摘要**和**事实检索**。如果你做的不是这两件事，就要当心你所选模型的分心上限。

### 上下文混淆

上下文混淆是指模型利用了上下文中多余的内容，从而生成了低质量的回答。

有那么一阵子，似乎人人都要发布一个 MCP。一个强大模型、连着你所有的服务和数据、替你完成所有琐碎任务的梦想，仿佛触手可及。只需把所有工具描述丢进提示词，然后启动即可。Claude 的系统提示词给我们指了路——它几乎全是工具定义或使用工具的指令。

但即便整合与竞争不会放慢 MCP 的节奏，上下文混淆也会。事实证明，"工具太多"这种事确实存在。

Berkeley Function-Calling Leaderboard 是一个工具使用基准，用于评估模型有效利用工具来回应提示词的能力。目前已更新到第三版，该榜单显示：当提供超过一个工具时，每个模型的表现都会变差。此外，Berkeley 团队设计了"所有提供的函数都不相关"的场景，期望模型输出"不调用任何函数"，然而所有模型仍会偶尔调用不相关的工具。

浏览该函数调用榜单，你会发现模型越小，问题越严重：

一个鲜明的上下文混淆例子来自最近的一篇论文，该论文在 GeoEngine 基准（一个包含 46 种不同工具的测试）上评估了小模型的表现。当团队给一个量化（压缩）后的 Llama 3.1 8B 模型连同全部 46 个工具一起的问题时，它失败了——尽管上下文远未超过 16k 的上下文窗口。而当只给模型 19 个工具时，它成功了。

问题在于：只要把东西放进上下文，模型就必须关注它。它可能是无关的信息或无谓的工具定义，但模型都会纳入考虑。大模型（尤其是推理模型）正在变得越来越善于忽略或丢弃多余的上下文，但我们仍不断看到无价值的信息绊倒智能体。更长的上下文让我们能塞进更多信息，但这种能力也带来了代价。

### 上下文冲突

上下文冲突是指你在上下文中积累了与其他信息相矛盾的新信息和新工具。

这是上下文混淆更麻烦的版本：这里的坏上下文并非无关，而是直接与提示词中的其他信息相冲突。

微软与 Salesforce 团队在最近一篇论文中精彩地记录了这一现象。该团队从多个基准中取出提示词，并将其信息分片到多个提示词中。可以这样理解：有时候，你坐下来，在按下回车前，把每一个必要的细节逐段输入 ChatGPT 或 Claude；另一些时候，你可能先从一个简单的提示词开始，等聊天机器人的回答不满意了，再补充更多细节。微软/Salesforce 团队把基准提示词改造成这种多轮交换的形式：

左侧提示词中的所有信息，都包含在右侧的多条消息中，这些消息会在多轮对话中逐步展开。

分片后的提示词带来了大幅度的结果退化，平均下降 39%。而且团队测试了一系列模型——OpenAI 备受推崇的 o3 的得分从 98.1 降到了 64.1。

这是怎么回事？为什么信息分阶段收集，而不是一次性给出时，模型的表现会更差？

答案是上下文混淆：组装起来的上下文包含了整个聊天交互，其中含有模型在掌握全部信息之前、为回答挑战而做出的早期尝试。这些错误答案始终留在上下文中，并在模型生成最终答案时影响它。团队写道：

> 我们发现，大语言模型往往在早期回合就做出假设，并过早地尝试生成最终解决方案，且过度依赖这些方案。简而言之，我们发现：当大语言模型在对话中走错一步，就会迷失方向，无法恢复。

这对智能体构建者来说可不是好兆头。智能体从文档、工具调用，以及被委派处理子问题的其他模型那里组装上下文。所有这些来自不同来源的上下文，都有可能彼此矛盾。此外，当你连接到自己没有创建的 MCP 工具时，它们的描述和指令与提示词其余部分相冲突的几率就更大。

百万 token 上下文窗口的到来曾让人感觉具有变革性。能把智能体可能需要的所有东西都丢进提示词，激发了人们对超级智能助手的想象——它们能访问任何文档、连接每一个工具、并保持完美记忆。

但正如我们所见，更大的上下文会催生新的失效模式。上下文毒化会把随时间累积的错误嵌入其中；上下文分心会让智能体过度依赖其上下文、重复过去的动作而非向前推进；上下文混淆会导致无关工具或文档被使用；上下文冲突则制造出内部矛盾，让推理脱轨。

这些失效对智能体的打击最为沉重，因为智能体恰恰运行在上下文急剧膨胀的场景中：从多个来源收集信息、顺序调用工具、进行多轮推理、并累积大量历史。

幸运的是，解决方案是存在的！在接下来的一篇文章中，我们将介绍缓解或避免这些问题的技术，从动态加载工具的方法，到建立上下文隔离区（context quarantine）。
