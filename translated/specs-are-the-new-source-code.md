# 规格已死，规格万岁！

## Ravi on Product（Ravi 的产品专栏）

### 原型是新的规格，而规格是新的……源代码？

作者：Ravi Mehta 与 Danny Martinez

2025年7月31日

纵观我的职业生涯，规格说明（spec）变得越来越短。我刚加入微软时，PM 的份量是用他们写的规格的厚度来衡量的。多年后在 Tripadvisor，我们神话了一位把规格——潦草地写在餐巾纸上——带进产品评审的 PM。

产品团队常常把规格说明当作文书工作——是"真正工作"（发布）之前不得不做的苦差事。工程师因优雅的代码而受到赞誉，设计师因漂亮的用户体验而受到赞誉。PM 因交付影响力而得到认可。但规格呢？它们通常被草草写完、扔到一边、然后遗忘。

这一直是个错误。在我的《产品能力工具箱》中，功能规格说明（Feature Specification）位居榜首——十二项能力中的第一项——这是有原因的。它支撑着产品执行（Product Execution），与产品交付（Product Delivery）和产品质量（Product Quality）并列。

无瑕的执行是优秀产品管理的基础，而一份出色的规格就是起跑线。

如今，我们构建产品的方式正在转变。工程师变得越来越快——快得多。AI 能在几分钟内把粗略想法变成可运行的代码。瓶颈不再是"构建"，而是"知道该构建什么"，以及让团队围绕这些需求对齐。

突然间，这份卑微的规格说明不再是转瞬即逝的文书，而是产品管理的基础——它正在变成源代码本身。

## 为什么 PM 突然成了瓶颈

在最近的演讲《用 AI 更快地构建》中，吴恩达（Andrew Ng）指出了一个前所未有的趋势：

> "这是我人生中第一次看到，管理者向我提议 PM 的数量是工程师的两倍。我还不知道这个提议是不是好主意，但我认为它是世界走向的一个信号。"——吴恩达

这印证了我们在上一篇文章中的预测：随着工程师借助 AI 以数倍的速度交付，公司需要更多的 PM 来支撑这些高产工程师，而不是更少。

随着产品交付加速，这给产品管理的其他每个方面都带来了巨大压力——理解客户需求、打磨正确的功能、验证影响力。

而这些压力全部汇聚到一件产出物上——规格说明。

## 规格——新的源代码

在传统软件开发中，程序员编写人类可读的"源代码"，它被编译成高度优化的、机器可读的"目标代码"。"目标代码"（也叫二进制文件）是一种副产品，可以靠源代码重新生成。源代码名副其实地是真相的源头（source of truth）。

来自 OpenAI 的 Sean Grove 提出了一个颇具挑衅性的论点。在近期的演讲《新代码》中，他认为一份精心编写的提示词（即规格说明）就是新的源代码。

从这个角度看，我们的 AI 开发方式搞反了。我们精心雕琢提示词，向模型传达我们的意图。AI 生成代码。然后我们保留代码，把提示词扔掉。

> "这感觉就像你把源代码撕碎，然后小心翼翼地给二进制文件做版本管理。"Grove 如此观察。

想想这一点。在传统编程中，源代码是神圣的。源代码包含注释、结构和文档——理解与修改系统所需的一切。二进制文件只是一个下游产物。

但有了 AI，我们把这种关系颠倒了。我们把生成的代码当作值得保留的产物，而把规格说明——提示词——当作一次性的。

Grove 认为这恰好弄反了。代码，即便是优雅的代码，是他所说的来自规格说明的"有损投影"（lossy projection）。正如反编译二进制文件不会还你原始的注释和变量名，阅读代码也不会告诉你它背后的完整意图。

然而，规格说明包含了一切。一份足够健壮的规格可以生成"优秀的 TypeScript、优秀的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客"。

> "一份足够健壮的规格可以生成优秀的 TypeScript、优秀的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客。"——Sean Grove，OpenAI

更重要的是，规格说明做到了代码做不到的事：它让人类和机器在共同目标上对齐。Grove 说得简明扼要："一份书面规格能有效地让人类对齐，它是你用来沟通、讨论、辩论、引用和同步的那件产物。"

他预测："在不久的将来，沟通最有效的人就是最有价值的程序员。而且毫不夸张地说，如果你能有效沟通，你就能编程。"

新的稀缺技能不再是编码，而是编写能够完整捕捉意图和价值观的规格说明。

对产品经理来说，这应该很熟悉。这正是我们一直在做的事——只是现在机器也在听了。

## 等等，难道不是原型杀死了规格吗？

直到最近，产品生命周期都不得不从规格（或 PRD、概念文档、餐巾纸）开始，它推动着最初的线框图、设计、原型和 MVP 开发。

传统做法感觉像是一种必要之恶。工程师构建基础 MVP，好把点什么东西——任何东西——交到客户手里。"如果你不为产品的第一版感到尴尬，那你发布得太晚了"成了金科玉律。

我们构建产品的整套方法最近经历了一次重大转变，在这个新世界里，规格常常是输出，而非输入。

如今，你一行代码都不用发布，就能把原型交到客户手里。v0、Lovable 和 Replit 这类工具让你在几小时内（而非几周）构建出可用的原型。无需工程背景。

这不只是更快——而是根本性的不同。带着一个"氛围编程"出来的原型，你可以在写一行功能规格之前就收集真实的客户反馈。你可以测试假设、迭代流程、打磨交互。

旧的工作流是这样的：

```
模糊的想法 → 线框图 → 设计 → 工程师构建的 MVP → 客户反馈
→ 痛苦的规格修订 → 线框图 → 设计 → 重建 → 祈祷
```

新的工作流：

```
模糊的想法 → 快速原型 → 客户反馈 → 水晶般清晰的规格 → AI 辅助实现
```

原型并没有杀死规格，它们让规格变得更好。

## 规格驱动开发实战

我们来看一个实操例子，看看这一切是如何展开的。Danny Martinez 是 decimals 的创始人，这是一个（尚处隐身状态）平台，帮助创作者经济中的专家把他们人脉网络里的人才安排到工作岗位。

Danny 将带我们走一遍他们的规格驱动开发流程——这个流程带来了两方面的影响：

1. 对较大的功能，极大地改善了与工程的沟通；
2. 让 Danny 在没有编程经验的情况下，也能对小功能从详细规格一路做到上线。

以下是 Danny 的自述……

这是我最近做的一个例子。作为背景，我们在构建一个产品，帮助专家型网红把网络中的人才安排到工作岗位。上线一个新的落地页后，我们需要给专家们一个快速获取自己页面链接的方式。

> "我们需要在页头加一个按钮，指向公司申请页。我现在在忙着处理邮件。这个很适合氛围编程，如果你能接手的话请帮个忙。"

这是我联创发来的消息，指的是一个需要上线的简单按钮。足够简单，也正是如今非技术人员可以自己上线的那类事。

下面是在几分钟内完成上线的设置和步骤：

- 项目管理工具：Linear
- IDE：VS Code
- 扩展：GitHub Copilot Pro
- 模型：Claude Sonnet 4
- MCP 服务器：Linear MCP server，让 Copilot 可以访问 Linear 工单

我们来看看流程中的各个步骤（可参考上方 Loom 视频）：

1. 根据联创的 Slack 消息生成一个 Linear 工单（00:14）
2. 在上面的工单里明确我希望新文案是什么（00:25）
3. 打开 Copilot，让 Claude 打开这个 Linear 工单（01:18）
4. 让 Claude 审查工单，并相对代码库分析它（01:52）
5. 让 Claude 创建分支并实现这些改动（02:30）
6. 测试改动，确保按预期工作（02:52）
7. 在 GitHub 上开一个拉取请求（PR），把这些改动合入代码库（03:55）
8. 等工程师审查/批准这个 PR

把镜头拉远，这套配置真正的威力就显现出来了。没错，这是个微不足道的例子，但关键在于：一个非技术人员如今可以靠几句通过 GitHub Copilot 发给 Claude 的提示词，在 Linear 工单、代码库和工程师之间自如穿梭。

而且，这一切的关键部分仍然不是代码本身：而是规格。

现在，有必要为以上内容加一个重要的前提，说明它要运作良好需要什么：

- **具体明确**：使用含糊的规格只会得到一团糟的代码库。用 Claude 对工单初稿进行审查、审视代码库并帮助让它更具体，是这个流程中不可或缺的一环。在我们的情况里，我们还为写好规格制定了一些准则。
- **有所取舍**：把上述方法用于较简单的任务是理想的。工单越复杂，就越需要一个懂行的人介入（在这些情况下，"自助"最终一点也不自助）。
- **把关**：这种方法之所以运转良好，是因为有一位真正懂行的工程师在审查改动，确保简洁与功能之间的平衡得以维持。

但我们要说清楚：规则已经变了。规格是每个参与构建产品的人——包括 LLM——的真相源头。

有了合适的配置，作为非技术人员为代码库做贡献是完全现实的预期。只要有足够的时间和耐心，你就可以开始理解代码库并亲自实现改动，而不是每次都依赖 Claude 来兜底。

有一天，你甚至可能期望一个 AI 智能体在你啜饮咖啡时把你的工单交付上线。

如果你是一名 PM，担心 AI 会对你的工作做什么，关键是意识到这份工作本身正在改变。但对其他所有人来说也是如此。好消息是，一名优秀 PM 所需的核心技能，在这个新世界里变得更加宝贵。

正如我们在上一篇文章中预测的那样，以这种方式运作的公司将需要更多而非更少的 PM。而事实证明，这个预测相当准确：

**规格万岁！**

科幻作家威廉·吉布森（William Gibson）创造了"赛博空间"（cyberspace）一词，他曾说：

> "未来已经到来——只是分布得还不均匀。"

当我思考 AI 能做什么、不能做什么时，我想起了这句话。今天，AI 的进展极不均匀。有些事情——生成代码、文本、图像——取得了质的飞跃，它们以"AI 的速度"运转。另一些事情——与客户交谈、发现他们的需求、说服他们购买——仍以人类的速度运转。

这种不均匀的分布正在重塑产品团队。聚光灯正从"实现工作"转向"理解工作"。那些一直让最优秀 PM 脱颖而出的核心技能——理解用户需求、清晰地定义问题、设计优雅的解决方案——正变得呈指数级地更有价值。

最优秀的 PM 把这些洞察转化为规格——这些规格对齐团队、指引实现，并在这个日益自动化的开发世界里充当持久的产物。
